## What this commit does

Splits the `authorizer.Authorizer` interface into two: introduces `UnconditionalAuthorizer` (holding the classic `Authorize` method) and reduces `Authorizer` to embed it (with a TODO for the conditions-aware methods to follow in `6d78dfd60cf`). Symmetrically renames the admission-initializer interface `WantsAuthorizer` → `WantsUnconditionalAuthorizer` and its setter `SetAuthorizer` → `SetUnconditionalAuthorizer`. Migrates every in-tree call site that previously took `authorizer.Authorizer` but only calls `Authorize()` to take the narrower `UnconditionalAuthorizer` instead. Adds a scattering of `var _ = authorizer.Authorizer(&T{})` assertions to keep implementers pinned to the full interface.

## Findings

### Critical (must fix before merge)

1. **`WantsAuthorizer` → `WantsUnconditionalAuthorizer` is an incompatible public API rename.** `staging/src/k8s.io/apiserver/pkg/admission/initializer/interfaces.go:47`. This interface is a public extension point used by third-party admission plugins written against `k8s.io/apiserver`. Any external plugin that implements `SetAuthorizer(authorizer.Authorizer)` will silently stop being initialised after this rename — the type assertion in `pluginInitializer.Initialize` (`initializer.go:94`) simply becomes `false`, and the plugin runs without an authorizer. This is a **security-relevant silent failure**: an admission plugin that relies on secondary auth checks (a common pattern) will suddenly find its `authorizer` field nil and either panic or (worse) fail-open depending on how the plugin handles the nil case. Suggested mitigations, in decreasing preference:
   - Keep both `WantsAuthorizer` (deprecated, still setting a full Authorizer) *and* the new `WantsUnconditionalAuthorizer`, with the initializer trying both. Mark `WantsAuthorizer` as deprecated for removal in +2 minor.
   - Or: keep the original name `WantsAuthorizer` and change the *type* of the setter argument to `UnconditionalAuthorizer` — implementers survive since Go interfaces are structural and `Authorizer` embeds `UnconditionalAuthorizer`.
   - Only rename if there is an explicit deprecation cycle documented in the KEP and release notes.

### Important (should fix)

1. **`var _ = authorizer.Authorizer(alwaysAllowAuthorizer{})` uses assignment, not blank identifier declaration.** `staging/src/k8s.io/apiserver/pkg/authorization/authorizerfactory/builtin.go:27–29,58–60,78`. The Go idiom is `var _ authorizer.Authorizer = alwaysAllowAuthorizer{}` (type on the LHS), which compiles to a no-op — the current form declares a package-level variable of type `authorizer.Authorizer` with a computed value, meaning the value is retained through program lifetime. It's harmless in practice, but non-idiomatic and future refactoring tools may flag it. Same pattern in `plugin/pkg/auth/authorizer/rbac/rbac.go:50–51` and elsewhere added by this commit.
2. **The doc comment on the reduced `Authorizer` interface still refers to unspecified "conditions-aware methods".** `staging/src/k8s.io/apiserver/pkg/authorization/authorizer/interfaces.go:99–105`. The `TODO(luxas): Add the conditions-aware methods in a follow-up PR.` marker is helpful, but at HEAD of this commit `Authorizer` is behaviourally identical to `UnconditionalAuthorizer`. The comment "one might choose whether to pass the Authorizer or smaller UnconditionalAuthorizer interface, depending on whether the receiver should be able to perform conditional authorization or not" doesn't apply until the follow-up. Consider deferring the comment until the follow-up commit lands, or add "(currently identical; will diverge in the next commit)".
3. **`pluginInitializer` field type widening removes an ability without warning.** `staging/src/k8s.io/apiserver/pkg/admission/initializer/initializer.go:33`. The stored `authorizer` field is now `UnconditionalAuthorizer`. If a plugin registered later needs a full `Authorizer` for conditions-aware auth checks, it cannot get one back from the initializer even by type-asserting — the concrete type is thrown away. A future `WantsAuthorizer` (conditions-aware) will need a separate field. Consider whether to store the original `Authorizer` and downcast when calling `SetUnconditionalAuthorizer`.

A quick `grep -rn "authorizer\.Authorizer" -- pkg/ plugin/ staging/` after this commit should show only sites that legitimately need the full interface (e.g. the SAR REST handlers). - Method rename `SetAuthorizer` → `SetUnconditionalAuthorizer` doubles the method's length; the "unconditional" is redundant given the setter matches the interface name. Optional: keep the method name `SetAuthorizer` on `WantsUnconditionalAuthorizer` — Go interfaces don't require method-name/interface-name symmetry.
- `staging/src/k8s.io/apiserver/pkg/endpoints/filters/impersonation/mode.go`: 22 hunks, mostly identifier renames. Since impersonation is a security-critical filter, an explicit callout in the commit body confirming that `UnconditionalAuthorizer` is intentionally used (impersonation cannot be conditional) would help future auditors.
- Test file assertions (e.g. `admission_test.go:` 42 hunks) suggest a wide test-touch surface — verify none of the moved code accidentally converted an `Authorizer` to `UnconditionalAuthorizer` in a place where a conditions-aware receiver was intended (spot-check the SAR REST tests).

### Questions

- Was there a discussion of "just rename `Authorizer` → `UnconditionalAuthorizer` at the package level and add a new `ConditionalAuthorizer` interface"? The current design keeps `Authorizer` as the full interface (with conditions-aware methods coming), which forces every implementer to grow — is that intended? Section §Core interface changes of `kep.md` matches the current shape, but the naming asymmetry (Authorizer=full, UnconditionalAuthorizer=narrow) is a subtle inversion that seems intentional. A short design note here would help.
- Why keep both `WantsAuthorizer` (removed) and add `WantsUnconditionalAuthorizer` (new)? A hypothetical future `WantsConditionsAwareAuthorizer` interface for admission plugins that need to react to conditional decisions (e.g. the `AuthorizationConditionsEnforcer` plugin itself) would fit here. This commit's rename may need to be paired with an added `WantsAuthorizer` (or renamed to `WantsConditionsAwareAuthorizer`) later. Confirm intent.

## What's well done

- The `UnconditionalAuthorizer` interface is scoped exactly right: a single method, no `RuleResolver` bundled in, no `conditions.go` symbols leaked. That's the right cut point.
- Adding `var _ = authorizer.Authorizer(&T{})` for the in-tree authorizers (`alwaysAllow`, `alwaysDeny`, `privilegedGroup`, `RBAC`, etc.) pins those types to the full interface — later commits that grow `Authorizer` will surface compile errors in exactly the right places.
- Doc comment on the new `UnconditionalAuthorizer` clearly signals it's the "downscoped" variant, which will read well once the conditions-aware methods land.

## Verdict

**Needs revision.** The `WantsAuthorizer` rename is a public API break with a security-adjacent silent-failure mode (admission plugins running without their authorizer). Fix that (either keep the old name or provide both) and the rest is a fine mechanical refactor.
