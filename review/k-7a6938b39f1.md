## What this commit does

Adds a single top-level function `PartiallyEvaluateConditionsAwareDecision(ctx, decision, data, evalFn)` that walks a `ConditionsAwareDecision` tree depth-first, evaluating what it can and preserving what it can't. The intended use case (per the KEP) is future built-in evaluators (e.g. a CEL evaluator) that recognise a subset of condition types and want to return a partially-reduced decision to be re-fed to the authorizer for the residue.

Semantics:
- On a `ConditionsMap` leaf, delegates to `partiallyEvaluateConditionsMapInternal`.
- On a `Union` node, iterates in order:
  - If a sub-decision has been (previously in the walk) resolved to `NoOpinion`, keep walking.
  - If a sub-decision resolves to `Allow` or `Deny` unconditionally, short-circuit and return.
  - If a sub-decision is still conditional after partial evaluation, keep walking but collect the *tail* without further evaluation (they belong to authorizers that come after a conditional, and evaluating them out of order would violate the lazy-chain semantics).
- On an unconditional leaf, return as-is.

Also adds a 442-line `evaluate_test.go` covering the partial evaluation surface.

## Findings

### Critical (must fix before merge)

None.

### Important (should fix)

1. **The `collectTailAfterConditionalDecision` variable name is opaque.** `evaluate.go:239`. What it actually models is "we've committed to leaving the rest of the chain unevaluated, because the next sub-decision is (still) conditional and depending on its evaluation result, later decisions may or may not fire". A clearer name: `restIsResidue`, `tailIsUnevaluated`, or `stopEvaluatingFurtherSubDecisions`. The comment two lines below says essentially this.
2. **`PartiallyEvaluateConditionsAwareDecision` is recursive; a maliciously crafted Union tree could cause stack overflow.** `evaluate.go:247`. Union depth is bounded only by the tree depth an authorizer chooses to return. Given the recursion is depth-first with a Go call per level, ~1000-deep unions would blow the stack. Two mitigations: (a) add an explicit depth cap (e.g. 64) in the recursion, returning fail-closed on exceed; (b) rewrite to an iterative traversal with an explicit stack. Given authorizers are somewhat trusted (they were configured via `AuthorizationConfiguration`), this is low priority — but it should be at least a documented invariant.
3. **The recursive walk uses `unevaluatedDecision.UnionedDecisions()` (an `iter.Seq2`) — the ordering guarantee should be documented.** `evaluate.go:242`. The chain-order semantics of the KEP rely on evaluations happening in the order the union was built. `iter.Seq2` doesn't in general guarantee order; the specific implementation (backed by the underlying `[]namedConditionsAwareDecision` in `conditionsunion.go`) does. Add a doc pointer.
4. **When the recursive call on a sub-decision returns a partial `Union` result (not just a leaf ConditionsMap), the outer walk's `collectTailAfterConditionalDecision` fires — but the returned tree may already have some evaluated leaves.** `evaluate.go:264–266`. So an inner Union that partially reduced (e.g. `[Allow after conditional, ConditionsMap]`) will have its residual re-inserted via `newDecisionChain.Add(name, possiblyEvaluatedSubDecision)`. Subsequent outer-level `Add` calls stop evaluating. That's correct semantically, but the invariant "everything up to a `ConditionsMap`/`Union` sub-decision is fully evaluated" is subtle. Add a doc comment: `// After partial evaluation, subDecision is either unconditional or contains at least one still-unevaluated leaf; the tail is preserved verbatim after that point.`
5. **The `default` branch returns `unevaluatedDecision` verbatim for `Allow`/`Deny`/`NoOpinion`.** `evaluate.go:275–277`. Correct, but the doc comment says "No simplification possible" — that's misleading since the decision is already fully evaluated (no simplification *needed*). Reword.

### Nits

- Comment typo: `"collectAndShortcircuitOnly == true"` (`evaluate.go:245`) doesn't correspond to any variable in the code; should be `collectTailAfterConditionalDecision == true`. This is a leftover from an earlier iteration of the code.
- The comment `"The logic in this function should be the same as in the union authorizer's ConditionsAwareAuthorize."` (`evaluate.go:241`) is a great cross-reference. If the two ever diverge, tests should catch it.
- `possiblyEvaluatedSubDecision` (line 260) is a nice name — signals uncertainty about the result state.
- 442-line test file for a 55-line implementation — great ratio.

### Questions

- If `evaluateConditionFn` is nil, does `PartiallyEvaluateConditionsAwareDecision` still make progress? Yes — the `Condition.Evaluate()` fast-path might still evaluate. Verified in the internal test file. Add an explicit doc note: "If `evaluateConditionFn` is nil, only conditions with a non-nil `Condition.Evaluate` will be reducible."
- Should `PartiallyEvaluateConditionsAwareDecision` be a method on `ConditionsAwareDecision`? The current top-level form makes it clear that this is a walking algorithm, not a decision property. Fine as-is.

## What's well done

- The invariant "if `collectTailAfterConditionalDecision`, every subsequent sub-decision is added verbatim" preserves the lazy-chain semantics. This is the key correctness argument.
- Cross-referencing the union authorizer's `ConditionsAwareAuthorize` (which uses the *same* iteration pattern for building the outbound decision) via the comment at line 241 is a good breadcrumb.
- Returning `newDecisionChain.ToDecision()` at both exit points ensures the result is either a folded unconditional decision or a well-formed Union — no half-built builder escapes.

## Tests

### Test files touched
- `evaluate_test.go` new, +442 — single `TestPartiallyEvaluateConditionsAwareDecision` table with fine-grained cases. Uses `github.com/google/go-cmp/cmp` for structural diffing of `ConditionsAwareDecision` snapshots (via a `snapDecision` helper).

### Coverage
- **Well covered:**
  - Leaf `ConditionsMap` variants: fully evaluated (all conditions in the builtin), partially evaluated (some Unevaluatable), fold to unconditional (all conditions evaluated to `false`).
  - `Union` traversal: three-way behaviour — all sub-decisions evaluate to NoOpinion (fold to NoOpinion), one sub-decision short-circuits to Allow (return early), one sub-decision remains conditional and the tail is preserved verbatim.
  - The `MaybeEvaluateConditionFunc` returning `Unevaluatable` for conditions of unknown type — this is the design case for the future built-in CEL evaluator.
- **Missing / thin:**
  - **Recursion depth**: no test asserts what happens with a deeply nested Union (Union-of-Union-of-…). The recursion in `evaluate.go:247` is unbounded; a 1000-deep tree would blow the stack. Add a stack-depth guard test.
  - **`evaluateConditionFn == nil`**: the function accepts nil (see the `!result.IsUnevaluatable() && evaluateConditionFn != nil` guard in `partiallyEvaluateConditionsMapInternal`). Tests should exercise nil evaluate-fn to ensure conditions with `Condition.Evaluate` fast-path still get evaluated.
  - **Union of only-unconditional sub-decisions**: e.g. `Union{Allow, Deny}` — the tail should short-circuit at the Allow. Verify a row for this shape.
  - **A `Union` sub-decision that is itself an Allow/Deny leaf** — should short-circuit immediately. Boundary case.
  - **Iterator early-exit safety**: the walk uses `range` over `UnionedDecisions() iter.Seq2`. A `return` inside the range aborts the iterator; verify no `defer`s in the closure are affected. (Should be a non-issue given the code, but a test with a panic in the closure would document behaviour.)
- **Feature-gate on/off:** N/A.

### Structure
- The `mkCM(items ...effectCondition)` helper (`evaluate_test.go:36–50`) plus the `cnd(effect, id, condition, typ, desc)` builder (`:52–60`) form a small mini-DSL for constructing ConditionsMap fixtures. Nice.
- The `snapDecision` structural comparison via `go-cmp` is a good choice — better than string equality against `String()` output.
- 442 lines — reasonable for the surface. Consider grouping cases into subtest groups (`t.Run("leaf/…", …)`, `t.Run("union/…", …)`) for readability.

Stale leftover from an earlier iteration.

## Verdict

**LGTM with nits.** The design is sound and well-tested. The variable-name and comment cleanups (Important #1, Nit #1) improve future maintainability; the recursion-depth cap (Important #2) is a real concern for hardening but low-severity in practice.
