## 3. Adversarial review

### Security

**S1. [Important] [code] `UnconditionalPartsOrFailClosed` has zero production callers. The 403-not-500 fold it was built for exists nowhere in production.**
- Locations: `authorizer/conditions.go:181-198`, `plugin/pkg/authorizer/webhook/webhook.go:264-267`, `endpoints/filters/authorization.go:115-118,208-221`.
- The only callers are three test fakes: `conditionsenforcer_test.go:92`, `filters/authorization_test.go:324`, `conditions_test.go:1127`. `git log -S` shows no production caller was ever added: the method appeared in `2e7e058110b`, and `7b20be8ae61` used it only in tests.
- The design intent was relocated, with changed semantics:
  1. **Webhook legacy `Authorize`** (`webhook.go:264-267`) receives an unrequested `conditionalDecision`. It computes `FailureDecision()` inline and returns an error. The legacy filter turns that error into a 500 (`authorization.go:115-118`) unless another authorizer Allows. That is exactly the 500 that `OrFailClosed`'s doc (`conditions.go:180`) promises to avoid. It is defensible as "protocol violation = server error", but it is the opposite of what this PR set up.
  2. **Structural avoidance.** Only conditions-aware call sites call `ConditionsAwareAuthorize`: the filter's classifier branch (`authorization.go:163-164`) and the SAR registries. A conditional decision therefore never reaches a conditions-unaware consumer that would need to fold it (shipped.md §3 item 2).
  3. **Filter, conditional decision without a possible Allow** (`authorization.go:208-221`). Example: a deny-only `ConditionsMap`, or a Union with possible outcomes ⊆ {Deny, NoOpinion}. The filter uses `Reason()`=`""` and `Error()`=nil, so it returns a 403 with an empty reason and an empty `authorization.k8s.io/reason` audit annotation. This is the spot `OrFailClosed` was designed for, and it was not used. `filters/authorization_test.go:465` pins the empty reason for gate-on. The gate-off expectation at `:463` shows the descriptive reason only because the test fake calls `OrFailClosed`.
- Why it matters:
  - The exported API advertises a fold that nothing uses, so out-of-tree implementers will copy it from the doc.
  - The real behaviour is either 500 (webhook) or a reasonless 403 (filter), and audit loses why the request was denied.
- Fix (one line): in the filter's non-Allow branch, use `conditionsAwareDecision.UnconditionalPartsOrFailClosed()` for reason and error. Then either use `OrFailClosed` in `webhook.go:264-267` (and settle Q1) or move it into a test helper package.

**S2. [Nit] [code] `OrFailClosed`'s reason string tells the requester that a conditional Allow path existed.**
- Location: `authorizer/conditions.go:192-196`.
- The string has the form "…possible outcomes [Allow NoOpinion]…". Once wired into a 403 body (S1), it tells the requester that some policy would have allowed them under conditions. RBAC already discloses comparable detail ("RBAC: clusterrole … not found"), so this is low risk. It should be a deliberate choice.
- Fix: decide on and document the disclosure. Optionally drop the outcome list from the client-facing reason and keep it only in the audit annotation.

**S3. [Question] [code+KEP] The `*.k8s.io` / `*.kubernetes.io` reservation for condition IDs and types is documented but not enforced anywhere.**
- Where the reservation is documented: `staging/src/k8s.io/api/authorization/v1/types.go:437,454`, `authorizer/interfaces.go:265,271`.
- Where it is not enforced: `validateConditions` (`conditionsmap.go:197,208`) accepts any domain. Declarative validation `k8s-prefixed-label-key` (`content/kube.go:107-117`) is character-equivalent to `IsDomainPrefixedKey`: both run `IsLabelKey` and then require exactly 2 `/`-segments, so neither checks the domain.
- What a webhook can do today:
  - Emit `type: authorizer.kubernetes.io/cel` and have it evaluated in-process (`interfaces.go:350`). This is the intended use.
  - Emit any other reserved type, e.g. `foo.kubernetes.io/x`. Today that goes to the webhook.
- Risk:
  - Future-compat hazard, the security-relevant part: if a later release adds a built-in evaluator for a reserved type, conditions a webhook already emits under that type silently switch evaluator. That is a semantics change in an access-control decision. The reservation is exactly what is supposed to prevent this, and it is unenforced.
  - Reserved IDs only matter for spoofing Kubernetes-looking IDs in denial reasons (`evaluate.go` "condition 'x' denied").
- Fix: while still alpha, reject types under the reserved domains other than the registered built-ins (`ConditionTypeAuthorizationCEL`), or drop the reservation for IDs and keep it only for types.

**S4. [Nit] [code] Constructor and declarative-validation errors echo the raw webhook-supplied ID/type into 500 response bodies.**
- Locations: `authorizer/conditionsmap.go:197-199,208-210`, `endpoints/handlers/responsewriters/errors.go:84`.
- `field.Invalid(..., key, ...)` renders `%q` of the full value with no truncation (`apimachinery/pkg/util/validation/field/errors.go:130-131`). The fail-closed decision carries it as `Error()`. The filter writes it verbatim (`InternalError` prints `%v` of the error). An over-long ID (e.g. a multi-KB prefix) is reflected into the client response and into logs.
- The source is the configured webhook, which is a trusted party. So this is information hygiene plus log amplification, not attacker control.
- Fix: truncate or omit the bad value (`field.Invalid(fldPath, field.OmitValueType{}, …)`) in `validateConditions`.

**S5. [Nit] [code] Unbounded `strings.Split` on webhook-supplied keys (liggitt's deferred T2).**
- Locations: `apimachinery/pkg/api/validate/content/kube.go:45`, `apimachinery/pkg/util/validation/validation.go:138`.
- A key such as `a/a/a/…` allocates one string per `/` before it is rejected. The input is bounded by the webhook response size; a trusted-but-buggy webhook can still burn memory per request.
- Fix: `SplitN(value, "/", 3)` in both helpers (the standalone PR liggitt asked for).

**S6. [Question] [code] Limits are per map only; nothing bounds a whole decision.**
- Locations: `authorizer/conditionsmap.go:116-122`, `conditionsunion.go:58`.
- Worst case per `ConditionsMap`: 128 × (10240 + 1024 + ~317 bytes of ID/type) ≈ 1.45 MB of condition material.
- A Union has no count or depth limit in-process. Declarative validation on `union` is list-map uniqueness only (D §3.4).
- The total is bounded only by the webhook response size and JSON depth limits. With #143024 each condition is compiled per evaluation (Q3).
- Fix: add a `MaxUnionEntries` and nesting-depth bound in `Add`/`ToDecision` and the decoder, or document why the response-size bound suffices.

Also checked, no issue found:
- **Fail-open:** every rule this PR added only removes acceptance. All of them go through `makeFailClosedError` (Deny if any Deny condition exists, else NoOpinion; `conditionsmap.go:141-146`) or the union's `FailureDecision`. No new path returns Allow.
- **Explicit Deny wins:** in `webhook.go:258-263`, an explicit `Denied` is checked before the unrequested conditional, so Deny still wins.
- **Gate-off reachability:** with the gate off, `ConditionsAwareAuthorize` has no callers, so the new rules do not apply. The rename and the warning are the only gate-off-visible changes (see Clarity).

### Bugs

**B1. [Nit] [code] The PR made the built-in superuser authorizer name collide-able with a user-configured name. A collision gives a confusing hard failure.**
- Locations: `pkg/kubeapiserver/authorizer/reload.go:117-121,256-259`, `apiserver/pkg/apis/apiserver/validation/validation.go:639-642`.
- Before this PR the built-in name `kubernetes.io/system-privileged-group` was not DNS-1123, and config names must be (`validation.go:633`), so a collision was impossible. Now a user name `system-privileged-group.authorizer.kubernetes.io` passes validation with only a warning.
- `union.New` then fails with `duplicate AuthorizerName`. At startup this is fatal. On reload the old config stays in place and an error is logged.
- The code comment at `validation.go:637-638` claims reserved names are only warned "so users are not forced to change the name" first. For the built-in names, users are in fact already forced.
- Fix: in `ValidateAuthorizationConfiguration`, reject exactly the names of authorizers that kube-apiserver adds itself.

**B2. [Nit] [code] DNS-1123 is enforced at the wrong layer for in-process unions.**
- Locations: `authorizer/conditionsunion.go:70`, `authorization/union/union.go:57-73`.
- `union.New` validates only empty and duplicate names. A non-DNS-1123 `NamedAuthorizer.AuthorizerName` is accepted at construction. Then:
  - Every `ConditionsAwareAuthorize` call fails closed through `ToDecision` (`conditionsunion.go:138-141`).
  - With an RBAC Allow in the chain, `FailureDecision` is NoOpinion and the error turns into a 500 at the filter.
  - The legacy `Authorize` keeps working.
- In-tree names are all valid on HEAD. Out-of-tree compositions that copied the pre-PR form (`kubernetes.io/foo`) break only with the gate on, and only per request.
- Fix: apply `IsDNS1123Subdomain` in `union.New` and return the error at construction.

**B3. [Nit] [code] `ConditionsMap.Evaluate` panics with a nil `evaluateConditionFn` although its doc says "if set".**
- Location: `authorizer/evaluate.go:99-111`.
- The wrapper closure calls `evaluateConditionFn` unconditionally (`:106`). Any condition whose own `Evaluate` returns unevaluatable triggers a nil function call.
- This PR edited this function (`.UnconditionalPartsOrError()` at `:111`, comment at `:105`). The comment "we never return unevaluatable" is true only when the function is non-nil.
- No production caller on HEAD.
- Fix: guard nil (return `ConditionEvaluationResultError`), or document "must be non-nil".

Also checked, no issue found:
- **Zero value:** `ConditionsAwareDecision{}` → Deny in both splitters (`conditions_test.go:1700-1704`).
- **Ordering:** in `validateConditions`, duplicate check → ID format → body size → type → description. A duplicate ID is reported only after the first occurrence passed format validation, so the duplicate error's echoed ID is bounded.
- **Add collects errors without short-circuiting** (by design, `conditionsunion.go:66-67`). A single empty name records two errors, both tested (`conditionsunion_test.go:75`).
- **`UnconditionalPartsOrError`'s default branch is unreachable in production:** `webhook.go:443-444` guards it with `IsUnconditional`, and `evaluate.go:111` is total when the function is non-nil.

### Clarity / completeness

**C1. [Important] [code] User-visible, ungated change in 403 messages and SAR output from the rename, combined with the #137513 prefix.**
- Locations: `authorization/union/union.go:88-89`, `conditionsunion.go:204-208`.
- The legacy `Authorize` aggregation prefixes NoOpinion reasons with `<name>: `. Two consequences:
  - kube-apiserver can now emit `system-privileged-group.authorizer.kubernetes.io: Error` (`authorizerfactory/builtin.go:117`, nil user).
  - Every delegating apiserver now shows `webhook.authorizer.kubernetes.io: <kube-apiserver reason>` in 403s. Before 1.38 the reason was unprefixed.

  - Legacy: `name: reason` (`union.go:89`).

- The same request can therefore get differently formatted 403 messages depending on the classifier (shipped.md Q9).

## 5. Verdict

Sound for alpha in the security sense:
- Every rule the PR added narrows acceptance and fails closed through `FailureDecision`. No new Allow path exists.
- The gate-off impact is limited to reason text, a log line, and one newly possible name collision.

The PR's central design artefact is `UnconditionalPartsOrFailClosed`, a fold for conditions-unaware consumers that yields a descriptive 403 instead of a 500. It was never wired into production:
- the webhook's legacy path folds inline and returns an error (500);
- the conditions-aware filter answers a non-allowable conditional decision with a reasonless 403;
- the only callers are test fakes, which makes some filter and enforcer test rows assert the fake rather than the system.

Before beta:
1. Decide Q1 (500 vs 403) and either use the helper in the filter and webhook or delete it.
2. Enforce, or drop, the `*.k8s.io` / `*.kubernetes.io` reservation for condition types, so that adding a future built-in evaluator cannot silently change the evaluation of existing webhook conditions.
3. Add a total-count rule to API validation, or correct the "128 in total" API doc.
4. Reject the built-in authorizer names in config validation.
5. Unify and release-note the union reason prefix.

The single most important finding is S1: the fail-closed-to-403 behaviour this PR exists to provide is dead code on HEAD. As a result, deny-only conditional decisions produce empty 403 reasons and empty audit reasons, and unrequested conditional webhook answers produce 500s.
