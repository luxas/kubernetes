## What this commit does

Turns the webhook authorizer into a real conditions-aware client. Additions:

- **`WebhookAuthorizer.ConditionsAwareAuthorize`** (~65 lines) — sends the SAR with `authorizationOptions.handledDecisionTypes` set, decodes any returned `status.conditionalDecision` via the new `apiserverauthorizationv1.DeserializeConditionsAwareDecision`.
- **`WebhookAuthorizer.EvaluateConditions`** (~100 lines) — the big new function. Sends an `AuthorizationConditionsReview` with the previously-returned `Decision` plus an `AdmissionRequest` built from the `ConditionsData`. Generates a fresh UUID for the request, validates that the response echoes it back, checks the response `Decision.Type` is within the previously-declared `PossibleDecisions`, and returns the classic triple.
- **`AuthorizationConfiguration.Webhook.ConditionsReview` YAML field** (`apis/apiserver/types.go` + v1/v1alpha1/v1beta1 conversions + validation) — allows operators to configure the ACR endpoint (`version` + optional `kubeConfigContextName`).
- **`v1alpha1.AuthorizationConditionsReview` typed client** — new `authorizationconditionsreviews` REST client under `client-go`.
- **`round_trip_test.go` update** (13 lines) — presumably registers the v1alpha1 scheme.
- **`webhook_conditional_test.go`** (new, 1023 lines) — comprehensive tests for the new conditions-aware paths.
- **`sendSARWebhook`** helper — extracted from `Authorize()` to avoid duplication with `ConditionsAwareAuthorize`.
- **`shouldFailWithDeny`** helper — decides fail-closed direction when a webhook returned a conditional decision to a legacy (`Authorize`) call site.

## Findings

### Critical (must fix before merge)

1. **The classic `Authorize` path silently returns `NoOpinion` when a webhook returns a conditional decision to a non-conditions-aware caller.** `webhook.go:250–266`. Specifically:
   ```go
   case r.Status.ConditionalDecision != nil:
       if shouldFailWithDeny(*r.Status.ConditionalDecision) {
           return authorizer.DecisionDeny, r.Status.Reason, fmt.Errorf("...tried to return conditional decision although client does not support it")
       }
       return authorizer.DecisionNoOpinion, r.Status.Reason, fmt.Errorf(...)
   ```
   The behaviour matches the KEP (fail closed to Deny if any Deny condition exists, else NoOpinion), and this is exactly what `FailureDecision()` does. But the classic `Authorize` path *should not have received* a conditional decision in the first place — the client's SAR request in this path did NOT include `authorizationOptions.handledDecisionTypes` (or included the unconditional set only). If the webhook still returns a conditional decision, that's a *webhook contract violation*. Consider elevating this to a Deny + audit annotation regardless, so operators know their webhook is misbehaving. Currently NoOpinion silently masks the violation.
2. **`sendSARWebhook` sends the SAR with the same `Spec` regardless of whether the caller is `Authorize` (unconditional) or `ConditionsAwareAuthorize` (conditional).** `webhook.go:230+`. But `ConditionsAwareAuthorize` (line 213 or thereabouts) sets `r.Spec.AuthorizationOptions.HandledDecisionTypes = ...` — verify. If the classic path forgets to unset `HandledDecisionTypes` when re-using a cached SAR spec, we could accidentally get conditional responses back to `Authorize`. Read the code carefully for this.
3. **`admissionv1.AdmissionRequest` construction has a bug: `RequestKind: new(metav1.GroupVersionKind(data.GetKind()))`.** `webhook.go:341+`. This looks like invalid Go — `new(T)` allocates a new pointer to the zero value, not a pointer to the argument. This code shouldn't compile. Confirm by building at this SHA. If it does compile, then `new` is being (mis)used with a type conversion. Either way, verify. If the code as-shown is correct, add a doc comment; if not, this is a compile-time break.

### Important (should fix)

1. **`convertToAuthenticationExtra` is duplicated with `convertToSARExtra` — the two do the same thing.** `webhook.go:687–698`. Consider a helper generic.
2. **The UUID correlation check is critical for security — verify no cache path bypasses it.** `webhook.go:418–420`: if `result.Response.UID != evaluateRequestUUID`, fail closed. This is exactly the pattern the KEP mandates. But `sendSARWebhook` caches SAR responses (`w.responseCache.Add(...)`), and the *ACR* path uses `authorizationConditionsReviewer.Create` directly without caching. Confirm ACR responses are never cached (they cannot be — the response is tied to the request UID).
3. **`EvaluateConditions` returns `authorizer.DecisionNoOpinion` if `result.Response == nil`.** `webhook.go:414`. This is a bug: if the webhook errored out at HTTP-level, we should surface an error, not silently NoOpinion. Consider `return decision.FailureDecision(), "failed closed", fmt.Errorf("webhook returned nil response")`.
4. **`DeserializeConditionsAwareDecision` takes a `failClosed func(error) authorizer.ConditionsAwareDecision` callback.** `webhook.go:271` — passes `w.conditionsAwareFailureDecision`. That callback returns Deny or NoOpinion based on `w.decisionOnError`. This means webhook-level `decisionOnError` config leaks into decision decoding logic; consider whether this is the right composition or if `FailureDecision()` should be used consistently.
5. **`shouldFailWithDeny` walks the whole decision tree recursively.** `webhook.go:270–288`. For a Union tree with many leaves, this is O(N). Not a hot path (it's only called on the classic-`Authorize` bail-out path), but worth noting.
6. **`AdmissionRequest.OldObject` is populated from `data.GetOldObject()` — for CREATE it should be nil.** `webhook.go:349–351`. If `data.GetOldObject()` returns nil, `runtime.RawExtension{Object: nil}` should serialize to null. Verify with a round-trip test.

## What's well done

- The UUID correlation between ACR request and response (`webhook.go:317, 418–420`) — exactly what the KEP prescribes. This prevents cache-substitution attacks where a stale ACR response might be interpreted as answering the current request.
- The `PossibleDecisions` post-check on the ACR response (`webhook.go:426, 431, 436`) — ensures a misbehaving webhook cannot return an unexpected concrete decision.
- Separating `sendSARWebhook` from the surrounding logic reduces duplication.
- `ConditionsReview` YAML block is a clean opt-in for operators — SAR endpoints unchanged, ACR endpoint separately configurable.
- 321-line validation test for `apis/apiserver/validation/validation.go` extends coverage for the new `ConditionsReview` block.
- 252-line encoding_test.go — round-trip verification of every decision-type variant.
