- `ConditionsMap` holds three unexported slices with the invariant deny ∪ allow ≠ ∅ (`A/conditionsmap.go:34-43`). It has `FailureDecision`, `Length`, ordered iterators and `PossibleDecisions` = {NoOpinion} ∪ {Allow if any allow condition} ∪ {Deny if any deny condition} (`:50-112`).
- `ConditionsAwareDecisionConditionsMap(deny, noOpinion, allow)` (`A/conditionsmap.go:138-185`):
  - 0 conditions → NoOpinion + error.
  - More than 128 conditions in total → fails closed.
  - Only NoOpinion conditions → folds to NoOpinion.
  - Validation: IDs unique across all lists, ID and type are domain-prefixed keys (#140715), condition ≤ 10240 bytes, description ≤ 1024 bytes (#140715).
  - Fail-closed value: Deny iff any deny condition, otherwise NoOpinion. Input slices are cloned.
  - `GenericCondition` (`:224-254`): a nil `EvaluateFunc` returns Unevaluatable.
- `ConditionsAwareDecisionUnion` is a builder (`A/conditionsunion.go:37-50`):
  - `Add` (`:58-84`) does nothing once an unconditional Allow/Deny leaf has been seen. Otherwise it records errors for an empty, duplicate or (since #140715) non-DNS-1123 name, but still appends. It also memoizes `containsUnconditionalAllowOrDeny` and the union of the children's PossibleDecisions.
  - `PossibleDecisions` (`:116-129`) = {NoOpinion} ∪ ⋃children, minus NoOpinion if an Allow/Deny leaf exists.
  - `ToDecision` (`:135-185`): if any error was recorded, returns `FromParts(FailureDecision, "failed closed", aggregate)`. If PossibleDecisions is a singleton, folds to an unconditional decision with reasons and errors collected recursively from matching leaves (`collectReasonsAndErrors`, `:187-208`). Otherwise returns a Union that clones the builder state.

### 3. Adversarial review

#### Security

PossibleDecisions soundness (checked, no finding):
- For a ConditionsMap, PossibleDecisions = {NoOpinion} ∪ {Allow | allow≠∅} ∪ {Deny | deny≠∅} (`A/conditionsmap.go:103-112`). This contains every result `A/evaluate.go:121-195` can produce: Deny comes only from deny-effect conditions that are true or error, and Allow only from a true allow-effect condition.
- For a Union, NoOpinion ∈ PD(c) ⟺ ¬ContainsUnconditionalAllowOrDeny(c), by induction: a map always has NoOpinion; Allow/Deny leaves never do. Because `Add` stops after the first child with such a leaf, every earlier child can yield NoOpinion. So every child's Allow/Deny is reachable under independence, and `A/conditionsunion.go:116-129` is exact when conditions are independent and an over-approximation when they are correlated.
- `ToDecision` folds only on a singleton set (`:144`), which is sound.
- FailureDecision ∈ PD holds for every variant except unconditional Allow (see Bugs).

- **[Important] [code] Constructor fail-closed ignores the webhook's failurePolicy** -- `A/conditionsmap.go:139-146,154-174`; caller `staging/src/k8s.io/apiserver/pkg/apis/authorization/v1/encoding.go:136-142` via `webhook.go:340`.
  - Explanation: an invalid ConditionsMap returned by a webhook gets the constructor's fixed rule: Deny iff any deny condition, otherwise NoOpinion + error. `failClosed` (= `conditionsAwareFailureDecision`, honouring `failurePolicy`) is only used for an unknown `type`. The same holds for an invalid Union (`A/conditionsunion.go:138-141`). shipped.md fact 5 lists inputs that pass DV but fail the constructor: more than 128 conditions in total across lists (DV allows 128 per list), and the same ID in two lists. With `failurePolicy: Deny`, such a response from an allow-only webhook becomes NoOpinion, and later authorizers are consulted.
  - Why it matters: the operator's configured fail-closed policy is silently downgraded for exactly the class of malformed responses the second validation layer exists to catch. This also contradicts kep.md:744-745,754-755,761-763,793-795 ("The FailureMode of the ConditionalAuthorizer determines how to handle invalid …").
  - Fix: add a validating constructor that returns `(ConditionsAwareDecision, error)` and have `ToAuthorizerConditionsAwareDecision` route the error to `failClosed`. Alternatively, make DV match the constructor (128 total, cross-list uniqueness).
- **[Important] [code] No bound on the size of a decision tree; the 128 cap is per map only** -- `A/conditionsmap.go:116,154`; `A/conditionsunion.go:58-90`; recursion in `A/conditions.go:271-286` and `A/conditionsunion.go:187-208`; API `staging/src/k8s.io/api/authorization/v1/types.go:587-594` (`union` has no `maxItems`).
  - Explanation: a Union can have any number of children at any depth, each holding a map of up to 128 conditions of ~11 KiB. `Add` checks for duplicates linearly (`:86-90`), so building is O(n²). `String`, `collectReasonsAndErrors` and the decoder (`encoding.go:144-148`) recurse without a depth limit.
  - Why it matters: a misbehaving or compromised webhook (SAR or ACR response) can make kube-apiserver burn CPU and memory on every request. The stated purpose of `MaxConditionsPerMap` is defeated by nesting.
  - Fix: cap union width (e.g. 32, matching the size of the authorizer chain), depth (e.g. 4) and total conditions per decision tree, in both DV and the builder.
- **[Question] [code] "Fail closed" to NoOpinion for deny-free inputs** -- `A/conditionsmap.go:145`; `A/conditionsunion.go:140`; `A/conditions.go:224-229`.
  - Explanation: an invalid allow-only map, or a union with a bad name and no Deny in its PossibleDecisions, becomes NoOpinion + error, and the chain continues to later authorizers.
  - Why it matters: this is sound relative to that authorizer's own power, since it could never deny, and it mirrors the KEP's NoOpinion-error semantics (kep.md:822-824). But it is weaker than the webhook's `failurePolicy: Deny` (finding above). Confirm it is intended outside the webhook path.
  - Fix: document on `FailureDecision` that "fail closed" means "never more permissive than this authorizer could have been".
- **[Nit] [code] Unvalidated webhook-controlled ID echoed into errors** -- `A/conditionsmap.go:190-192` (duplicate check before format/length validation at `:197`); `:198,209` (field.Invalid embeds the value).
  - Explanation: the ID text ends up in `Decision.Error()`, which reaches logs and possibly a 500 body. DV bounds it on the wire first, but the constructor alone does not.
  - Why it matters: low. Defence in depth.
  - Fix: validate the format and length before the duplicate check; truncate quoted values.
- **[Question] [code] `UnconditionalPartsOrFailClosed` reveals the possible outcomes in a 403 reason** -- `A/conditions.go:191-195`.
  - Explanation: no production caller yet (shipped.md fact 1). If it is adopted, a conditions-unaware client learns "you could be allowed conditionally".
  - Fix: decide whether that disclosure is acceptable to unprivileged callers before wiring it in.

Also checked, nothing further found:
- Gate bypass: the data model is ungated by design (thread #1). Only the webhook produces conditional decisions, and it is gated.
- Immutability: no exported mutator; slices are unexported; `PossibleDecisions` returns fresh sets (`A/conditions.go:207-215`, `A/conditionsmap.go:104`, `A/conditionsunion.go:119`). The builder clones the PD set (`:182`).
- Cache keys: not applicable to this layer.

#### Bugs

- **[Important] [code] `ConditionsMap.Evaluate` panics on a nil `evaluateConditionFn`** -- `A/evaluate.go:99-110` (Part B file; the thread #30 doc is in Part A).
  - Explanation: the doc says "secondarily using evaluateConditionFn, if set". The wrapper closure is always non-nil and calls `evaluateConditionFn` without a check, whenever a condition's own `Evaluate` returns Unevaluatable. `GenericCondition` without `EvaluateFunc` always does so (`A/conditionsmap.go:250-251`), as does every decoded webhook condition (`encoding.go:157`).
  - Why it matters: an out-of-tree authorizer that follows O-C7's suggested `conditionsMap.Evaluate(ctx, data, nil)` panics in the request path. The function has no in-tree caller (C §1.1).
  - Fix: if `evaluateConditionFn == nil`, return `ConditionEvaluationResultError("no evaluator")` (fail closed), or fix the doc. Part B should confirm.
- **[Nit] [code] Copying the builder by value aliases its state** -- `A/conditionsunion.go:37-50,78,80-83`.
  - Explanation: `u2 := u1` shares the `inner` backing array and the `subDecisionsPossibleDecisions` map, so `Add` on one copy changes the other's PossibleDecisions. The builder is exported, and only "not thread-safe" is documented.
  - Fix: document "must not be copied after first use" (or embed `noCopy`).
- **[Nit] [code] An unknown `decisionType` is inconsistent across accessors** -- `A/conditions.go:131-133` (IsDeny ⟺ ==0) vs `:214-215,224-229,318-320` (default branches treat it as Deny); `IsUnconditional` is false (`:154-156`).
  - Explanation: unreachable, because the enum is unexported and only set by constructors.
  - Why it matters: only for formal modelling.

### 5. Verdict

The data model is sound for alpha. I proved PossibleDecisions to be a sound over-approximation (exact under independence), and folding happens only on singletons, so no tree can fold to an outcome it could not reach. FailureDecision never yields Allow, and it is in PossibleDecisions for every conditional variant. Immutability holds for every in-tree Condition implementation.

Before beta:
1. Route constructor-validation failures of webhook responses through the configured `failurePolicy`, or make DV identical to the constructor.
2. Bound union width/depth and total conditions per decision tree.
3. Fix or document the nil-`evaluateConditionFn` panic in `ConditionsMap.Evaluate`.
4. Add a brute-force PossibleDecisions-soundness and fold-equivalence test.
5. Rewrite KEP §"Condition and ConditionSet data model" and §"chain", including that evaluation is eager rather than lazy.

The single most important finding: the constructor's fixed fail-closed rule overrides the webhook's `failurePolicy: Deny`, so some malformed allow-only responses become NoOpinion and let later authorizers decide.

### 3. Adversarial review

#### Security

Results for the special-focus question (a), precedence soundness. Checked: every return in `A/authorizer/evaluate.go:134-191` and the loop at :200-223.
- **A false Deny cannot mask a true Deny.** `false` results are `continue` (:211-212), and the first `true` returns Deny with a nil error (:138-142) no matter where it sits in the list.
- **An errored Allow cannot by itself yield Allow.** Allow is returned only when some Allow condition is `true` (:177-180), and only after every Deny and NoOpinion condition evaluated `false` (the earlier blocks return on any true, error or unevaluated result). An errored Allow with no true Allow gives NoOpinion plus the error (:182-183).
- **A Deny-effect error never weakens the decision.** It gives Deny plus the error (:144-145), whatever the unevaluated conditions are.

The only "masking" is of *errors*: a true condition drops errors from same-effect conditions (:209-210), and a Deny short-circuit drops the error lists of the other effects. This is deliberate (threads #67, #51) and safe.

**[Important] [code] Ungated, undiscussed change to 403 and SAR reason text; three different reason formats.** Locations: `A/union/union.go:88-89,92-93,99`; `A/authorizer/conditionsunion.go:192,162-170`; `A/union/union.go:180`.
- What changed: every kube-apiserver and delegating-authorizer `Authorize` now emits `"<authorizerName>: <reason>"` on the NoOpinion path, with the gate off. Examples:
  - `alwaysdeny: Everything is forbidden.` for **anonymous** users (`test/integration/controlplane/synthetic_controlplane_test.go:179`).
  - `node: no relationship found between node …` (`plugin/pkg/auth/authorizer/node/node_authorizer.go:239`).
  - A doubled `rbac: RBAC: …` (`plugin/pkg/auth/authorizer/rbac/rbac.go:127`). The name is `strings.ToLower(mode)`, from `pkg/kubeapiserver/authorizer/config.go:168`.
- Asymmetry: the Allow/Deny short-circuit stays unprefixed (`union.go:93`). For example, a webhook Deny reason or `RBAC: allowed by …` in SAR is unprefixed, while a NoOpinion reason from the same authorizer is prefixed.
- Third format: with the gate on, the conditions-aware fold in `ToDecision` uses `name: {reason}` joined with `", "` (`conditionsunion.go:192`). So the same request yields different text on the conditional path (writes) than on the legacy path (reads). The integration test `conditionalauthorization_test.go:1212` vs `:1256` encodes exactly this (`conditional-webhook: failed closed` vs `failed closed`; Q9).
- Why it matters:
  - It is a 1.37→1.38 user-visible change behind no gate. It discloses admin-chosen authorizer names and topology to unauthenticated clients and to anyone who can create a SelfSubjectAccessReview.
  - It breaks log or alert matching on 403 messages.
  - It is not in the KEP, and no thread discussed it. Special-focus question (c): it was not discussed.
- Fix: either revert the prefix in `Authorize` (keep it only in conditions-aware paths), or apply one format (`name: reason`) on all three paths, including short-circuit, and add a release note.

**[Question] [code] Name routing is not pinned to the union instance that produced the decision.** Locations: `pkg/kubeapiserver/authorizer/reload.go:97-98`, `A/union/union.go:188-194`.
- The filter stores the top-level authorizer, which is the `reloadableAuthorizerResolver` (`A/../endpoints/filters/authorization.go:170`; `server/config.go:1079`).
- The enforcer calls `authz.EvaluateConditions` on it (`conditionsenforcer.go:146`), which runs `r.current.Load()` at admission time.
- If the authorization config reloads between the filter and the enforcer, a ConditionsMap authored by the old authorizer named `X` is routed to whatever is now named `X`: a different webhook endpoint, or an RBAC instance (which fails closed through the guard at `union.go:163`).
- Conditions are opaque per authorizer, so a different authorizer evaluating them is a decision-tree confusion. A builtin CEL condition evaluates the same regardless of the authorizer.
- The window is one in-flight request per reload. The KEP's API doc requires names to be "stable over time" (`staging/src/k8s.io/api/authorization/v1/types.go:600`), but nothing enforces stability across a reload.
- Fix: store the concrete `r.current.Load().authorizer` snapshot in the request context instead of the resolver, or make the reloadable resolver route by generation.

**[Question] [code] An Allow-effect evaluation error becomes a 500 that echoes the evaluator error to the requester.** Locations: `A/authorizer/evaluate.go:182-183`, `:217`.
- The NoOpinion result carries `condition "<id>" with effect=Allow evaluated to an error: <err>`. If no later authorizer allows, the enforcer returns `apierrors.NewInternalError(err)` (`A/../admission/plugin/authorizer/conditionsenforcer/conditionsenforcer.go:128-130`).
- A requester who controls the object, for example by omitting a field a CEL expression dereferences, can force 500s and read condition IDs plus evaluator messages. They would get a 403 if errors were treated as `false`.
- The KEP says Allow errors are "ignored" (see K2).
- Fix: drop Allow-effect errors from the returned error (log them, or attach them as audit annotations) so the outcome is a 403, matching the KEP.

**[Nit] [code] Recursion and size of a webhook-supplied Union are bounded only per map.** Location: `A/authorizer/evaluate.go:262`.

- Each partial evaluation recurses once per level and evaluates up to 128 conditions per map.
- The webhook is admin-configured, so this is low risk.
- Fix: cap total conditions and depth in `ToAuthorizerConditionsAwareDecision`.

#### Bugs

**[Important] [code] `union.New` accepts names that the decision builder rejects. Every conditions-aware request then fails closed.** Locations: `A/union/union.go:57-68` vs `A/authorizer/conditionsunion.go:70-72`.
- `New` checks only empty and duplicate names. `ConditionsAwareDecisionUnion.Add` also requires a DNS-1123 subdomain and records an error otherwise, and `ToDecision` then returns `FailureDecision, "failed closed"` (`conditionsunion.go:138-141`) for **every** request, including an unconditional Allow from the first sub-authorizer.

Any out-of-tree or generic-apiserver caller of `union.New` with a name like `"my_authz"` or `"Foo"` loses all conditions-aware writes (403 or 500) once the gate is on, and `Authorize` keeps working. That divergence is hard to diagnose.
- `NamedAuthorizer`'s doc says the authorizer "must be non-nil" (`union.go:49`), but this is not checked. A nil authorizer panics at the first request.
- Fix: in `New`, validate `IsDNS1123Subdomain` and non-nil `Authorizer`, and return the error.

**[Important] [code/KEP] Partial-then-full evaluation is not confluent when the partial evaluator returns errors.** Location: `A/authorizer/evaluate.go:182-187` (also :144-149).
- Within an effect, error ranks above unevaluatable. In the Allow block, `{allow-err, allow-unevaluated}` gives `NoOpinion+err` and **discards** the unevaluated Allow condition. A full evaluation in which that condition is `true` gives Allow.
- The Deny block gives the same decision either way, but the error component differs (Deny+err, which becomes a 500, vs Deny with nil, which becomes a 403).
- The doc comment (:227-234) presents partial evaluation for "a subset of the conditions" with no precondition on errors.
- Today's only caller maps builtin errors to Unevaluatable (`webhook.go:966-971`, #143024), so in-tree behaviour is safe. The exported contract still allows a non-confluent, more restrictive result, and a 500 where a 403 or an Allow was due.
- Fix: in partial mode (any unevaluated condition present in the same effect), rank unevaluatable above error, that is, return a refined ConditionsMap keeping the unevaluated conditions. Or document "evaluateConditionFn must not return Error unless it is authoritative".

**[Nit] [code] `ConditionsMap.Evaluate` panics on a nil `evaluateConditionFn`.** Location: `A/authorizer/evaluate.go:104-111`.
- The adapter closure is always non-nil and calls `evaluateConditionFn` unconditionally (:106) whenever a condition self-reports unevaluatable, which is the case for every `GenericCondition` decoded from the wire (`encoding.go:157-162`).
- The internal function tolerates a nil function (:126), so the asymmetry is surprising.
- Fix: guard for nil and map it to an error result, or document the parameter as required.

**[Nit] [code] `union.EvaluateConditions` does not enforce the interface's non-nil `data` contract.** Locations: `A/union/union.go:131`; contract at `A/authorizer/interfaces.go:122`.
- Unit tests pass `nil` (`union_test.go:900`). The webhook checks for nil (`webhook.go:437-439`).
- Fix: fail closed on nil data at the union, the single entry point.

**[Nit] [code] Errors from earlier NoOpinion leaves are dropped when a later leaf Allows or Denies.** Locations: `A/union/union.go:171-172` and `:92-93`. This matches 1.37 `Authorize` and thread #51, and is recorded here as a property, not a bug.

### 5. Verdict

The evaluation core is sound for alpha. The effect precedence cannot be inverted: no false or errored condition can turn a true Deny into anything else, and no errored Allow can produce Allow. Every error path in the union evaluator fails closed to a FailureDecision that is within the relevant `PossibleDecisions`. Partial evaluation over Union trees short-circuits correctly and keeps names and positions. Before beta, fix the following:
- union.New must validate names the way the decision builder does (DNS-1123, non-nil).
- Define partial evaluation's handling of error vs unevaluatable so that partial-then-full is confluent, or document the precondition.
- Decide the Allow-error behaviour (KEP "ignored" vs code "500 with the error text").
- Pin the evaluating authorizer across reloads.
- Add the missing negative tests: New errors, unknown name, non-Union input, laziness, and names after partial evaluation.

The single most important finding is the **ungated, undiscussed change to `Authorize` reason text** (`A/union/union.go:88-93`). Since this merge, every kube-apiserver and aggregated-apiserver 403 and SAR reason on the NoOpinion path is prefixed with admin-chosen authorizer names, including for anonymous users. The Allow/Deny path is not prefixed, and the conditions-aware path uses yet another format. It is not in the KEP or any thread, and unit tests do not cover it.
