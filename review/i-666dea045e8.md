## What this commit does

Adds `evaluate.go` with the reference implementation of `ConditionsMap.Evaluate` and the internal partial-evaluation helper `partiallyEvaluateConditionsMapInternal`. Also adds:

- `ConditionEvaluationResult` — a small four-variant algebraic type (`True`/`False`/`Error`/`Unevaluatable`) so a `Condition.Evaluate` implementation can express "I can't answer this right now" for partial evaluation.
- `EvaluateConditionFunc` and `MaybeEvaluateConditionFunc` — top-level func types used by callers to plug in the evaluation strategy.
- `Condition.Evaluate(ctx, data) ConditionEvaluationResult` method added to the interface.
- `GenericCondition` grows an `EvaluateFunc` field; its `Evaluate()` returns `Unevaluatable` when the func is nil.
- ~487 lines of table-driven tests in `conditions_test.go`, plus ~686 lines of white-box internal tests in `evaluate_internal_test.go`. Huge test surface — this is the correctness core of the KEP.

## Findings

### Critical (must fix before merge)

1. **`conditionsToAppliedErroredUnevaluated` short-circuits Deny/NoOpinion evaluation on the *first true* condition — but silently drops accumulated errors.** `evaluate.go:` (see `return reason, nil, nil` on the true branch). Rationale in the comment: "nil is returned for errors here as the list is not comprehensive in the short-circuit case." But the *effect* is that a Deny condition that evaluates to true silently masks an error in a *previous* Deny condition. That's benign for allow/deny (Deny is Deny either way), but for NoOpinion it could mask a warning that would help debug a broken authorizer. Consider surfacing the accumulated `errs` via a `warning` or via `EvaluationError` on the returned decision. Given the review criteria for A09 (Security Logging and Alerting Failures), this dropped error is worth pushing back on.
2. **Order of iteration is `denyConditions → noOpinionConditions → allowConditions`, but within each slice the order is arbitrary — first `true` short-circuits.** `evaluate.go:141+`. That's a design choice with security implications: it means the *first* `denyCondition` to return `true` picks the reason surfaced to the user. If an authorizer authored two Deny conditions where one leaks sensitive information and the other doesn't, the leaky one may win. Not a bug per se, but worth documenting: "The reason surfaced for a Deny match is that of the first (in slice order) Deny condition that evaluated to true. Authorizers who care about which reason surfaces should order accordingly."

### Important (should fix)

1. **The `ConditionsMap.Evaluate` public API takes an `EvaluateConditionFunc` (returns `(bool, error)`), while `partiallyEvaluateConditionsMapInternal` uses `MaybeEvaluateConditionFunc` (returns `ConditionEvaluationResult`).** `evaluate.go:114–130`. The adapter (`evaluate.go:118–125`) converts `(bool, error)` → `ConditionEvaluationResult`. This is a small performance overhead per condition, and the two-tier design is confusing. Consider exporting only one — the `MaybeEvaluate...` variant is strictly more expressive — and making callers wrap their `(bool, error)` returns. Alternatively, keep both but rename `EvaluateConditionFunc` to `ConcreteEvaluateConditionFunc` for clarity.
2. **`conditionsToAppliedErroredUnevaluated` returns `("", errs, unevaluated)` when nothing is applied.** `evaluate.go:190–192`. The caller then decides based on whether `unevaluated` or `errs` is non-empty. But the priority is `errored > unevaluated`? No: looking at the caller (`evaluate.go:145–150`), it's `applied > errored > unevaluated`. This matches the comment "true > error > unevaluatable > false". Verify: If a Deny condition errors and another Deny condition is unevaluatable, we short-circuit to Deny with the aggregated errors. But the docs say the semantics are "first true; otherwise gather errors and unevaluated". The current code does exactly this, but the ordering between "errored" and "unevaluated" in the switch is not documented. Add a top-of-function comment: "Priority for aggregate result: (1) any applied → shortcut; (2) any errored → Deny; (3) any unevaluated → partial re-evaluate."
3. **The Deny/NoOpinion cases return `nil` for the aggregated `errs` on the true-shortcircuit branch,** but the Allow case also has a `// Errors could technically be returned with an Allow (and be logged), but no errors are returned...` comment (`evaluate.go:177–179`). Consistent behaviour is good; the trade-off is stated. Consider making the "log the swallowed errors even though we didn't surface them" step actually happen — a `klog.V(4).Info(...)` at the very least would give operators visibility into partial errors.
4. **`ConditionEvaluationResultError(nil)` fabricates a default error.** `evaluate.go:53–58`. Fine for defensive coding, but might silently mask a caller bug. Consider `panic("nil error passed to ConditionEvaluationResultError")` — this is not a runtime-callable path.
5. **`GenericCondition.Evaluate` returning `Unevaluatable` when `EvaluateFunc` is nil is asymmetric with `Evaluate` in other implementations.** `conditionsmap.go:228–232`. Consumers might expect `nil EvaluateFunc + call` to be a programmer error, not a silent unevaluatable. Since the fallback path in `partiallyEvaluateConditionsMapInternal` will then delegate to the caller-provided `EvaluateConditionFunc`, this is by design. Add a docstring pointing out that `EvaluateFunc == nil` means "always defer to the caller".

### Nits

- Typo in `interfaces.go:296`: `"Only the condition itself and data can infuence the outcome."` should be `influence`.
- The `partialConditionEvaluationResultType` enum uses `iota` starting from `0` for `Unevaluatable` — that's the zero value, which means the struct zero value is safe. Good.
- Function name `conditionsToAppliedErroredUnevaluated` is a mouthful. Consider `partitionByOutcome` or `firstMatchOrDetails`. Minor.
- `partiallyEvaluateConditionsMapInternal` is package-private but its function name is `partiallyEvaluate...` — the `partially` prefix is used in an exported top-level function name later (`PartiallyEvaluateConditionsAwareDecision`), causing a naming collision. Consider `partiallyEvaluateMapInternal` vs. `evaluatePartialMap`. Not blocking.
- 686 lines of internal test file is heavy; consider whether some cases are duplicated in `conditions_test.go`.

### Questions

- What's the runtime cost of the adapter closure in `ConditionsMap.Evaluate` (`evaluate.go:118`)? Not measured — but the closure allocates on every call. For hot paths (every write request when conditional authz is engaged), consider whether to expose `EvaluateWithMaybe` directly.
- The `[]Condition` returned to `ConditionsAwareDecisionConditionsMap` in the unevaluated case (`evaluate.go:153`) preserves order. But `partiallyEvaluateConditionsMapInternal` walks in Deny → NoOpinion → Allow order — if the caller re-invokes with the returned partial map, they get the same short-circuit priority. Good.

## What's well done

- `ConditionEvaluationResult` is well-scoped: True/False for concrete answers, Error for evaluation errors, Unevaluatable for "I can't evaluate this myself". This lets `Condition.Evaluate` be a fast path for pre-compiled conditions with a clean fallback story via `MaybeEvaluateConditionFunc`.
- The Deny > NoOpinion > Allow evaluation order is exactly what the KEP §"Computing a concrete decision from a ConditionsMap" specifies.
- The comment `// General logic: Deny > NoOpinion > Allow. Within a set of same-effect conditions true > error > unevaluatable > false.` (`evaluate.go:138–139`) is a great locator comment for future readers.
- 1156-line test suite (487 + 686) for a 225-line implementation is generous coverage; the internal-test file uses white-box access to sanity-check the partial-evaluation cases that black-box tests can't reach.
- The `GenericCondition.EvaluateFunc` optional field means implementers can wire in fast in-process evaluation without adding new types.

### Coverage
- **Well covered:**
  - `ConditionEvaluationResult`: all four constructors (`Boolean(true)`, `Boolean(false)`, `Error`, `Unevaluatable`) and all four predicates (`IsTrue`, `IsFalse`, `IsError`, `IsUnevaluatable`). Verified via helper closures at the top of `evaluate_internal_test.go`.
  - `partiallyEvaluateConditionsMapInternal` combinations: for each of Deny/NoOpinion/Allow, tests cover (a) first-true short-circuit, (b) all-false continue, (c) errored condition, (d) unevaluatable condition, (e) mixed error+unevaluatable, (f) empty slice. This is where the 686-line internal test file's bulk lives.
  - The precedence Deny > NoOpinion > Allow is exercised at the aggregate level.
  - Deny-condition short-circuits Allow-with-error (i.e. errors in the Allow slice never leak up to the caller if a Deny hits true).
  - The `EvaluateConditionFunc` fallback (when `Condition.Evaluate` returns `Unevaluatable`) is exercised.
- **Missing / thin:**
  - **The dropped-errors-on-short-circuit invariant** (Critical #1 in main review) is *asserted by* the tests but never *questioned by* them. A test that verifies the swallowed error is *not* surfaced would be helpful — and would document the trade-off precisely. Add a comment on one of the "first-true short-circuit with prior errors" test cases pointing at the design decision.
  - **Order-of-evaluation within a slice**: `conditionsToAppliedErroredUnevaluated` walks conditions in slice order. Tests assert that the *first* true condition's reason surfaces, but no test asserts what happens when two conditions in the same slice both evaluate to true — the second one's error is silently dropped (Critical #2). Add a "two true Deny conditions" row asserting the first one's reason wins.
  - **`ConditionEvaluationResultError(nil)`** — `evaluate.go:53–58` fabricates a default error with `errors.New("unspecified evaluation error")`. No test exercises this path (i.e. passing nil to the constructor). Not a common case, but a defensive branch worth pinning.
  - **`GenericCondition.Evaluate` with nil `EvaluateFunc`** returns `Unevaluatable` (`conditionsmap.go:228–232`). This is well covered via `unevalCond(id)` helper (`evaluate_internal_test.go:56`).
  - **Concurrency**: `Condition.Evaluate` docstring says `must be safe to call repeatedly and concurrently` (`interfaces.go:291`) — no concurrency test.
  - **Context cancellation**: `Evaluate` takes a `ctx` but the docstring says "should only be used for timeouts/cancellation/tracing, and should not influence the evaluation outcome" — no test that a cancelled context returns before evaluating (which is what a proper implementation would do).
