## 3. Adversarial review

### Security

- **[Important] [code] Re-using client-input SAR validation on SARs the server builds itself lets a client deterministically trip the webhook's failurePolicy on the conditions-aware path.**
  `staging/src/k8s.io/apiserver/plugin/pkg/authorizer/webhook/webhook.go:327`, which calls
  `CombinedValidateSubjectAccessReviewCreate`. That function runs `ValidateSubjectAccessReviewSpec` (`validation.go:37`)
  over the spec that the webhook built from request attributes (`webhook.go:275-301`, `resourceAttributesFrom` `:566-592`).
  `fields.ParseSelector` accepts an empty left-hand side (`staging/src/k8s.io/apimachinery/pkg/fields/selector.go:418-428`,
  `:446-452`). So a `deletecollection` with `?fieldSelector==x` is turned into `FieldSelectorRequirement{Key:"", Operator:In, Values:["x"]}`
  (`webhook.go:604-607`). `ValidateFieldSelectorRequirement` then reports `key: Required`
  (`apimachinery/pkg/apis/meta/v1/validation/validation.go:137-139`). The webhook was already called, but its answer is
  discarded and replaced with `conditionsAwareFailureDecision` (`webhook.go:347-352`). With `failurePolicy: NoOpinion`, a
  webhook explicit Deny becomes NoOpinion, and a later authorizer in the chain (for example RBAC) decides instead.
  The legacy `Authorize` path (`webhook.go:220-272`) does no such validation and returns the webhook's Deny.
  `deletecollection` is classified, so it takes the conditions-aware path when the gate is on
  (`pkg/controlplane/apiserver/config.go:299`, per shipped.md §3.3).
  Today the handler probably rejects the empty field label later, but that is coincidental: I did not verify it per resource or for CRDs.
  The PR's own goal ("accessible to the webhook authorizer") is what put these validators on this path, although the call site was added by #137633.
  -- why it matters: the client controls this input, it flips Deny to NoOpinion, and the two Authorize paths now disagree for the same request.
  -- fix: in the webhook, validate only the response status (`ValidateSubjectAccessReviewStatus` plus status DV), not the
  locally built spec; or make `fieldSelectorToAuthorizationAPI` drop empty-key requirements, consistent with "selectors only narrow".
- **[Question] [code] An empty user plus nil groups fails the same spec check on the conditions-aware path only.**
  `validation.go:45-47` vs `webhook.go:276-283`. If `attr.GetUser()` is nil or has an empty name and no groups, the
  conditions-aware path fails closed and the legacy path sends the request. I found no production caller that reaches
  `ConditionsAwareAuthorize` without a user (the filter requires authentication), so this is a question. The fix is the same as above.
- None found for: leakage (the validators return field errors that the webhook wraps into the decision error, not into the client reason; reason handling is #137633's scope), DoS (validators are linear in input; no recursion added by this PR), cache keys, impersonation (not touched).

### Bugs

- **[Nit] [code] The internal->v1 conversion is lossless for every field on HEAD, but the comment overstates why.**
  `pkg/apis/authorization/validation/validation.go:58,76,94` say the internal and v1 types are "byte-identical".
  That holds for every spec (`unsafe.Pointer` casts, `pkg/apis/authorization/v1/zz_generated.conversion.go:677-679`,
  `:573-575`, `:501-503`). It does not hold for `Status`: since #137633 the conversion is field-by-field with a manual
  recursive `ConditionsAwareDecision` converter (`zz_generated.conversion.go:709-725`, `pkg/apis/authorization/v1/conversion.go:33-34`).
  No converter reads the scope `s`, so `nil` is safe today. Nothing enforces that, and the kube path has no panic guard
  (unlike `CombinedValidate*`, `validation.go:320-324`). Every registry clears `Status` before validating
  (`pkg/registry/authorization/subjectaccessreview/rest.go:73`, `selfsubjectaccessreview/rest.go:74`,
  `localsubjectaccessreview/rest.go:75`), so validation never sees a status that conversion could mangle.
  Information loss that validation then misses: none found.
  -- fix: reword the comment to "lossless; scope unused", or pass a real scope via `scheme.Convert`, as the ACR path already does (`validation.go:111`).
- **[Nit] [code] The hard-coded field path ignores `fldPath`.** `validation.go:48,66` pass `field.NewPath("spec.resourceAttributes")`
  instead of `fldPath.Child("resourceAttributes")`. This predates the PR and the path is correct for every current caller.
  Now that the function is a public staging API, any caller with a non-`spec` root gets wrong error paths. -- fix: use `fldPath.Child(...)`.
- **[Nit] [code] The webhook composition appends handwritten and DV errors without the dedupe and alpha/beta gating that `rest.ValidateDeclaratively` does.**
  `validation.go:319-334`. The handwritten union error is `MarkCoveredByDeclarative` (`:40,43`) and the DV union is `MarkAlpha`
  (`staging/src/k8s.io/api/authorization/v1/zz_generated.validations.go:803,982`). Both are therefore reported, and alpha
  DV rules become authoritative on this path. Unreachable today, because the webhook always sets exactly one of
  resource or non-resource attributes. -- fix: drop errors marked covered-by-declarative, or document the double report.
- Byte-for-byte equivalence (focus a): verified at merge for all eight functions, including the field and label selector
  helpers (`AllowUnknownOperatorInRequirement: true` preserved, `:211-212`, `:233-234`) and the LocalSAR rules: metadata
  empty except namespace and managedFields (`:170-174`), namespace equals `spec.resourceAttributes.namespace` (`:176-178`),
  `nonResourceAttributes` disallowed (`:179-181`). No dropped case. On HEAD the functions are supersets: #137633 added the

- Generated-code drift (focus c): the staging and pkg v1 DV functions are textually identical at merge and on HEAD

  The kube path uses only the pkg copy (scheme-registered); the webhook path uses only the staging copy. Neither runs both.

## 5. Verdict

As a refactor, the merged code is sound. The moved validators are byte-for-byte equivalent to the removed ones. The
internal->v1 conversion is lossless, and its nil scope is safe on HEAD. The two generated DV copies are identical and
do not conflict. No test cases were lost. The title's "defaults" refers to nothing. The risk this PR enables, but did
not wire itself, is reusing client-input validation on SARs that the server synthesizes in the webhook's
conditions-aware path. Before beta, the webhook should validate only the webhook's response status (or sanitize
empty-key selector requirements), and a test should pin that `Authorize` and `ConditionsAwareAuthorize` agree on such
inputs. Most important finding: a client-chosen `fieldSelector==x` makes the conditions-aware webhook path discard the
webhook's answer and apply `failurePolicy`, turning a webhook Deny into NoOpinion under `failurePolicy: NoOpinion`
(`webhook.go:327`, `webhook.go:604-607`, `fields/selector.go:418-428`).
