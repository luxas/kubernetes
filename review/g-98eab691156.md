## What this commit does

Adds three reasoning helpers on `ConditionsAwareDecision`:

- `PossibleDecisions() sets.Set[Decision]` — returns the set of concrete outcomes the decision could evaluate to. For unconditional decisions, a single-element set. For the (still-not-implemented) conditional variants, the set will be `{Allow, NoOpinion}` for Allow-only conditions, `{Deny, NoOpinion}` for Deny/NoOpinion-only, etc.
- `FailureDecision() Decision` — the fail-closed unconditional decision to use if evaluation cannot proceed. Returns `DecisionDeny` if `PossibleDecisions().Has(DecisionDeny)`, else `DecisionNoOpinion`.
- `ContainsUnconditionalAllowOrDeny() bool` — a fast-path predicate for the union builder to know whether it can short-circuit.

The test file (`conditions_test.go`) grows from ~194 → 275 lines with new expectations for each of the three helpers across the existing table.

## Findings

### Critical (must fix before merge)

None.

### Important (should fix)

1. **`PossibleDecisions` `default` case returns `sets.New(DecisionDeny)` for `ConditionsMap`/`Union` variants — silently wrong once those variants exist.** `conditions.go:141–146`. The `switch` only handles `IsAllow`, `IsNoOpinion`, and `default → Deny`. For `IsConditionsMap` or `IsUnion` variants (added in the next two commits), this returns `{Deny}` — which will suppress a legitimate conditional Allow. The correct default must consult the map's / union's own `PossibleDecisions`. This absolutely needs to be corrected when the ConditionsMap/Union variants land, and until then any code that calls `PossibleDecisions()` on a conditional decision returns wrong results. Since no conditional decision *can* be constructed yet, no live wire is affected — but this is a landmine planted for the next commits. Two ways forward: (a) add a `panic("unreachable")` in the default until the variants are implemented, or (b) implement the ConditionsMap/Union cases now (even if there's no constructor yet, the enum values exist).
2. **`ContainsUnconditionalAllowOrDeny` has a typo in its docstring.** `conditions.go:167`: `"returns true whether there union contains at least one Allow or Deny"` — should read `"returns true if the decision's tree contains at least one unconditional Allow or Deny leaf"`. Grammar aside, the docstring says "the union" but the method is defined on `ConditionsAwareDecision`, not on a union type. Reword.
3. **`ContainsUnconditionalAllowOrDeny` body has a `if … { return true } return false // NoOpinion` pattern.** `conditions.go:168–172`. Could simply be `return d.IsAllow() || d.IsDeny()`. The `NoOpinion` comment on the last line is misleading — it captures only the case where the decision is NoOpinion, not conditional. Since conditional variants aren't yet constructible, this quirk is harmless today, but confusing.
4. **`FailureDecision` docstring says "encounters an unrecoverable error while processing a ConditionsAwareDecision"** (`conditions.go:150–156`) — but the code doesn't error on anything, it just picks Deny/NoOpinion from the possible set. That is, "failure" here means "we can't produce the concrete decision, so use this fail-closed one" — a slightly different notion of failure. The distinction matters when reading downstream code that surfaces this decision to callers. Consider clarifying: `// FailureDecision returns the fail-closed unconditional decision to use when the caller has decided not to (or cannot) proceed with the conditions-aware decision. If Deny is a possible outcome, returns Deny (fail closed); otherwise NoOpinion.`

### Nits

- `sets.New(DecisionDeny)` builds a fresh 1-element set on every call; consider a package-level `var possibleDeny = sets.New(DecisionDeny)` cache to avoid allocation on the hot path. Only relevant for hot paths — probably not measurably.
- `Set[Decision]` (using the K8s generic sets) is the right choice; matches the `sets` idiom used elsewhere in the KEP-side code.
- The three new methods are all defined without a `//nolint` for cyclomatic complexity — none should trigger it. Verify with `staticcheck`.

### Questions

- What's the intended caller for `ContainsUnconditionalAllowOrDeny`? Presumably the `ConditionsAwareDecisionUnion` builder's short-circuit logic in a later commit (`d725c326bcd`). Confirming this design intent guides whether the method should be exported (as it is) or package-private.
- Why is `FailureDecision` public? The KEP describes it as an authorizer-facing helper for folding back to unconditional. Confirm — public is fine, but the docs should point out the primary caller pattern.

## What's well done

- The `PossibleDecisions()` idea is a clean way to express "conditional but could still turn into Allow" without a dedicated `IsConditionalAllow`/`IsConditionalDeny` API. Later code (e.g. the request-classifier decision to let the request proceed in the HTTP filter) uses `PossibleDecisions().Has(DecisionAllow)` — a nicely composable primitive.
- The test-table structure is easy to grow: adding three fields (`wantPossibleDecisions`, `wantFailureDecision`, `wantContainsUnconditionalAllowOrDeny`) is enough to cover every existing case.

## Verdict

**Needs revision.** Landmine in `PossibleDecisions` default case (returns `{Deny}` for future ConditionsMap/Union variants — should either panic or be extended now); typo in docstring; minor readability nit in `ContainsUnconditionalAllowOrDeny`. All fixable in this commit.
