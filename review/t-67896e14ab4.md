## Findings

### Critical (must fix before merge)

1. **Silent fallback to `WithAuthorization` when "gate on but plugin off".** `authorization.go:120`. The conditions-aware filter only engages when all three are true: `featureGate.Enabled(ConditionalAuthorization) && conditionsEnforcerEnabled && classifier != nil`. If an operator enables the feature gate but disables the admission plugin (or the classifier is not installed), the API server silently reverts to the classic filter — no conditional decisions ever appear, no error, no warning. This is exactly the "silent misconfiguration" concern flagged in `changes.md`. Fix by adding a startup check: if `ConditionalAuthorization` is on and `ConditionsEnforcerPluginEnabled` is false, `AdmissionOptions.Validate` should return an error preventing API server start. See the KEP §Feature availability for the intended design.
2. **`Validate` in the plugin only checks `!c.featureEnabled` (early return) — no check that admission's `Attributes.GetOldObject()` is populated for UPDATE operations.** `conditionsenforcer.go:81+`. If the caller is `AdmissionConditionsEnforcer` (invoked as a validating plugin), the admission machinery should have populated `OldObject` for UPDATE — but a bug in a preceding mutating webhook could clear it. The plugin passes `versionedAttributes` through to `authz.EvaluateConditions`, which will see `nil` for oldObject and possibly evaluate conditions incorrectly. Defensive check: if operation is UPDATE and oldObject is nil, fail closed via `possiblyConditionalDecision.FailureDecision()`.
3. **`versionedAttributes.newVersionedAttributes` is a temporary re-implementation because `admission.NewVersionedAttributes` has a known bug.** `versioned_attrs.go:31–34`. The comment says `// TODO(luxas): This should be admission.NewVersionedAttributes, but that implementation by error does not override GetOldObject(). That should be fixed, but as a separate change (probably feature-gated).` This is *load-bearing*: if the upstream fix ships and this copy isn't removed, we'll have two divergent implementations. File a follow-up issue linked from this TODO.

### Important (should fix)

1. **`Handles(operation admission.Operation) bool` returns `c.featureEnabled` for all operations, including reads.** `conditionsenforcer.go:78–80`. That's fine for a validating plugin (it will be called with the operation Verbs specified by RESTStorage), but consider narrowing to only mutation verbs (`CREATE`, `UPDATE`, `DELETE`, `CONNECT`) since conditions never apply to reads. This is a defensive narrowing.
2. **The plugin's `Validate` function is 60+ lines with three fail-closed branches.** `conditionsenforcer.go:81–145`. Consider extracting the "guard against bad inputs" switch (lines 91–105) into a helper `assertExpectedInputDecision` that returns a boolean. Reads better and is easier to unit-test in isolation.
3. **On invalid input decision (e.g. `IsDeny()` reaching the enforcer), the plugin returns `apierrors.NewInternalError`** — HTTP 500. This is a server-side bug indicator, but the audit annotation only records `filters.ReasonError`. Consider adding a klog.Error to emit the specific inconsistency for operator diagnostics.
4. **`ConditionallyAuthorizedDecisionFrom` uses a value type assertion on `ctx.Value(...)` — if the context is not set, it returns the zero value of `authorizerDecisionTuple{}` (which has nil authorizer and empty decision) and `ok=false`.** `context.go:96–99`. Callers must check `ok` before using the returned authorizer. Confirm in every call site (the enforcer plugin does check; ripgrep the tree for `ConditionallyAuthorizedDecisionFrom` to be sure).
5. **Docstring typo**: `context.go:88` — `WithConditionallyAllowedDecision` mentioned in the doc, but the function is `WithConditionallyAuthorizedDecision`. Also `ConditionallyAuthorizedDecisionsFrom` (plural) in doc at line 98 vs `ConditionallyAuthorizedDecisionFrom` (singular) function name. Fix.
6. **The `PossibleDecisions().Has(decision)` post-`EvaluateConditions` check** at `conditionsenforcer.go:118–122` is a strong invariant enforcement — an authorizer that returns a Decision not previously listed in `PossibleDecisions()` is treated as a bug and folded to `FailureDecision()`. Good defensive coding.

### Nits

- The plugin's `NewConditionalAuthorizationEnforcer(featureEnabled bool)` constructor argument is defaulted to `false` in `Register` and then set correctly in `InspectFeatureGates`. The middle-of-flight state (registered as false but not yet inspected) is only present during initializer construction — no race concern.
- `conditionsenforcer.go:57` — `_ genericadmissioninit.WantsFeatures = &conditionsEnforcer{}` — the interface assertion pattern is right.
- `conditionsenforcer.go:97` — the switch case order `Deny/NoOpinion, IsConditionsMap/IsUnion, Allow, default` is not the most readable; consider `Allow → conditional → deny/noopinion → default` for a top-down "happy path first" reading.
- The metrics changes are consistent with the existing patterns; the new label `authorizationMetricsLabelForAuthorizeConditionsAware` is a mouthful but descriptive.
- `authorization_test.go` has +239 lines; verify test names cover: (1) FG off, (2) FG on + plugin off, (3) FG on + plugin on + classifier true, (4) FG on + plugin on + classifier false.
- Sample apiserver update — good; ensures downstream consumers see this pattern.

### Questions

- The `pkg/kubeapiserver/options/plugins.go` update adds the plugin to `DefaultOffAdmissionPlugins`. Why default-off if the feature gate is what actually controls enablement? Two levels of opt-in feels defensive; verify that the plugin ships enabled-by-default when the FG is on. Otherwise operators must both enable the FG and toggle `--enable-admission-plugins=AuthorizationConditionsEnforcer` — a paperwork trap.
- The classifier signature `func(attrs authorizer.Attributes) bool` is minimalist. Should it also receive the `context.Context` (for tracing/cancellation)? Currently it's synchronous and pure — probably fine.

## What's well done

- The context helper design (`WithConditionallyAuthorizedDecision(ctx, authorizer, decision)`) is exactly right: not just the decision, but the *authorizer that produced it* is threaded through. This means the enforcer can call `EvaluateConditions` on the same object, no lookup by name required.
- The "guarantees at least one of PossibleDecisions is returned" check (`conditionsenforcer.go:118–122`) is a strong defensive invariant that catches authorizer bugs at the earliest possible point.
- Audit-annotation emission consistent with `WithAuthorization` (`conditionsenforcer.go:124–128, 137–141`).
- Test coverage is heavy — 542 lines for a 146-line plugin, plus 239 lines added to the filter test file.
- The three-way enablement (FG + plugin + classifier) matches the KEP design and gives operators granular control.

## Verdict

**Needs revision.** Two Critical items: silent-misconfiguration fallback (should be a startup error, not a silent revert) and the `versionedAttributes` reimplementation follow-up (needs a tracked issue). Otherwise a substantive, well-tested piece of the KEP.
