- **Subject:** Pre-factor for conditional authz: AuthorizerNames are DNS 1123 subdomains, enforce length limits on conditions, require condition ID and type to be domain-qualified, and expose the UnconditionalParts convenience function.

## What this commit does

Four related tightenings:

1. **Domain-qualified `Condition.ID` and `Condition.Type`.** Switches from `content.IsLabelKey(...)` to `utilvalidation.IsDomainPrefixedKey(...)`, requiring `<domain>/<key>` format (e.g. `acme.io/foo`). Applies inside `validateConditions` in `conditionsmap.go`.
2. **Length limits.** New constants `MaxConditionBytes = 10240` and `MaxConditionDescriptionBytes = 1024`; validation added in `validateConditions`.
3. **DNS-1123 subdomain check on `authorizerName`.** Added inside `ConditionsAwareDecisionUnion.Add` via `utilvalidation.IsDNS1123Subdomain(authorizerName)`. Also renames the parameter `conditionalAuthorizerName` → `authorizerName`.
4. **Re-exposes `UnconditionalParts` (was `unconditionalParts`, private).** Reverses the "private for now" of the previous iteration.

Also adds a warning-only check in `apis/apiserver/validation/validation.go` for `AuthorizationConfiguration.Authorizers[].Name` values ending in `.k8s.io` or `.kubernetes.io` — this is only a klog warning, not a validation error, on the reasoning that a legacy operator may already have used such a name.

Reload path (`pkg/kubeapiserver/authorizer/reload.go`) and options wiring (`server/options/authorization.go`) touched to align.

## Findings

### Critical (must fix before merge)

1. **The `.k8s.io` / `.kubernetes.io` reservation is only a klog warning, not a validation error.** `staging/src/k8s.io/apiserver/pkg/apis/apiserver/validation/validation.go:641–648`. This is a policy hole. If a malicious operator names their custom authorizer `evil.k8s.io`, they can impersonate future Kubernetes-shipped conditions and shadow decisions. Two options:
   - Reject at validation time with an actionable error message.
   - Keep the warning but log-loudly, and add an `AuthorizationConfigurationReservedNameLoophole` feature gate that flips to hard-reject in the next release cycle.
   The commit comment "someone could technically have configured their Kube API server with such a name already" acknowledges the compatibility concern, but the current shape is a graduation hazard: once beta, users will depend on reserved-name authorizers working, and the tightening will be blocked. Prefer to reject now (before alpha ships), while the surface is still small.

### Important (should fix)

1. **`utilvalidation.IsDomainPrefixedKey` returns `field.ErrorList` requiring `.ToAggregate()` — the current caller uses `fmt.Errorf("invalid condition: %w", errs.ToAggregate())`.** `conditionsmap.go:197–199`. `field.ErrorList` has explicit paths; the wrapping loses them. If a caller wants to know *which* condition ID failed, they need to parse the message. Consider surfacing the individual `field.Error`s directly:
   ```go
   allErrs = append(allErrs, errs...)
   ```
   and returning `field.ErrorList` from `validateConditions`.
2. **Reserved-domain check uses `strings.HasSuffix` — matches `notk8s.io` too.** `validation.go:641–648`. Should be `strings.HasSuffix(a.Name, ".k8s.io") || a.Name == "k8s.io"` to match `foo.k8s.io` but not `notk8s.io`.
3. **`UnconditionalParts` is re-exported without adding a "safe to call regardless of decision variant" doc.** `conditions.go:158–160`. The docstring now says `This function is meant to be called when IsUnconditional() == true.` — but the code fallback (via `FailureDecision()`) makes it safe to call anyway. Reword to: `Also safe to call on conditional decisions, in which case FailureDecision() is returned along with a synthetic reason.`
4. **The `IsDNS1123Subdomain` check on `authorizerName` in `Add` is done *after* the empty-name check and duplicate-name check** — both accumulate errors before this. If an empty name is passed, we get *two* errors: "must be non-empty" and "invalid authorizerName: []" (empty string is invalid DNS-1123). Consider short-circuiting on empty name.
5. **The length limits are enforced only at construction time via the constructor.** If a `Condition` grows dynamically (e.g. a mutable implementation), the check doesn't re-fire. Since `Condition` is an interface, that's a real concern for third-party implementations. Document that conditions must be immutable — this is stated in the interface doc but bears repeating for security.
6. **`MaxConditionBytes = 10240` and `MaxConditionDescriptionBytes = 1024` are hard-coded.** For future flexibility, consider whether these should be exposed via `AuthorizationConfiguration` (e.g. `MaxConditionBytes` as a knob) — probably not necessary now, but note it as a possible extension point.

### Nits

- The rename `conditionalAuthorizerName` → `authorizerName` is a good simplification; the "conditional" was redundant (all authorizers in a union are conditions-aware by interface).
- `IsDomainPrefixedKey(field.NewPath("id"), id)` passes a synthetic `field.Path` since the check is not part of a broader API validation. Consider `field.NewPath("condition", "id")` for a more locatable error message.
- Rewording "invalid condition" as `"invalid condition %q"` (with the ID) would help operators know which condition failed.

### Questions

- Was there a discussion about whether authorizer names should be domain-qualified (like condition IDs)? Currently they must be DNS-1123 subdomains, which allows non-domain names like `myauthorizer`. Consistency with `condition.id/type` might be preferable.
- The re-exposure of `UnconditionalParts` — was the earlier removal a review overcorrection? The current shape (exported) is what the KEP describes.

## What's well done

- Making the domain-qualified constraint mandatory for `id` and `type` at construction time is exactly the KEP-mandated behaviour landing in the right place.
- The three limits (128 conditions, 10240 bytes body, 1024 bytes description) are all enforced by the same code path (`validateConditions`), so there's a single choke point to reason about.
- DNS-1123 subdomain for authorizer name matches the wire-format validation (see `NamedConditionsAwareDecision.authorizerName` in the API types).
