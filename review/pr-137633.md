### 3. Adversarial review

#### Security

**[Important] [code] DV-valid but constructor-rejected ConditionsMaps skip `failurePolicy=Deny`.** Locations: `staging/src/k8s.io/apiserver/pkg/apis/authorization/v1/encoding.go:134-142`, `staging/src/k8s.io/apiserver/pkg/authorization/authorizer/conditionsmap.go:150-156,166-174`.
- What happens: some webhook `conditionalDecision` values pass `CombinedValidateSubjectAccessReviewCreate` (`webhook.go:327`) but are then rejected by `ConditionsAwareDecisionConditionsMap`. These are `{type: ConditionsMap, conditionsMap: {}}`, a map with more than 128 conditions in total but at most 128 per list, and the same ID reused across the noOpinion and allow lists. When the map has no deny conditions, decoding returns NoOpinion+error. The `failClosed` callback, which is `conditionsAwareFailureDecision`, is never called. With `failurePolicy=Deny` the union then moves on, and RBAC can still Allow.
- Why it matters: the same kind of malformation caught one layer earlier (129 entries in one list, rejected by DV `maxItems`) gives Deny. So the result depends on which layer catches the bad response, and the admin's "errors → Deny" setting is bypassed for a protocol error. (Thread #87, still unresolved, asked for exactly this check.)
- Fix: in `ToAuthorizerConditionsAwareDecision`, send a constructor error decision through `failClosed`. Alternatively, add DV/handwritten rules: at least 1 condition in total, at most 128 in total, and IDs unique across lists.

**[Important] [code] Union width and depth have no bound.** Locations: `staging/src/k8s.io/api/authorization/v1/types.go:584-593` (no `maxItems`); recursion in `encoding.go:70-80,143-148`, `v1/zz_generated.validations.go:443`, and `conditionsunion.go:187-207`.
- What happens: a webhook response can nest `union` until it hits the JSON decoder's depth limit. Decode, DV, `PossibleDecisions` aggregation and `String()` all recurse over it. Combined with the missing response-size limit (row 25), one bad or compromised webhook answer costs unbounded CPU and memory per request, on every apiserver replica.
- Thread #48 agreed on 16 entries per level "for beta". Nothing in the code or the KEP tracks that.
- Fix: `+k8s:maxItems=16` on `union`, a depth cap in DV/decode, and a webhook response body limit.

**[Nit] [code] Reserved `*.k8s.io`/`*.kubernetes.io` IDs and types are documented but not enforced.** Locations: `v1/types.go:437,452-455`; `conditionsmap.go:197-210`; DV at `v1/zz_generated.validations.go:106,168`.
- Any webhook may emit any reserved type, not only `authorizer.kubernetes.io/cel`, which is the intended one and is evaluated in-process by #143024.
- Fix: enforce a reserved-type allowlist, or drop the word "reserved".

**[Question] [code] Unknown-type `failClosed` follows `failurePolicy=NoOpinion`, but v1beta1 uses Deny.** Locations: `encoding.go:149-150`; `webhook.go:265,341` pass `conditionsAwareFailureDecision`; `pkg/apis/authorization/v1beta1/conversion.go:67-69` passes Deny.
- In the legacy webhook `Authorize` path, the decision is decoded with no validation first (`webhook.go:262-266`). An unknown nested leaf becomes NoOpinion. The final result is still `FailureDecision()`, so this path never produces Allow.
- Question: should an undecodable decision always fail to Deny, regardless of `failurePolicy`?

Checked, and no issue found:
- (d) With `clientIsConditionsAware=false`, any non-nil `conditionalDecision` gets Forbidden (`validation.go:101-103`). In the webhook path the flag comes from the server-built spec (`webhook.go:276-299`, validated at `:327`), not from the webhook's echo. With the gate off, DV `ifDisabled=forbidden` blocks it again (`v1/zz_generated.validations.go:1114-1124`). So a conditional decision cannot pass.
- Gate bypass on SAR: options are cleared before validation (`rest.go:78-80`), and `ResolveAuthorizationOptions` checks the gate again (`pkg/registry/authorization/util/helpers.go:252`).
- (c) The v1beta1 fold-down never sets `allowed=true` (`conversion.go:77`). No real client can reach it: v1beta1 SAR is not served (`storage_authorization.go:39-52`), and a v1beta1 decode leaves `AuthorizationOptions` nil. The fuzzer nil-ing therefore hides no reachable lossy path.

### 5. Verdict

The API, validation, encoding and conversion layers are sound enough for alpha:
- No path found lets a conditional decision reach a client that did not opt in.
- The v1beta1 fold-down is conservative and unreachable from REST.
- Gate-off behaviour on the wire matches 1.37, apart from SAR status being cleared before `createValidation`.

Before beta:
- Close the gap between declarative validation (per-list limits, per-list ID uniqueness, empty maps accepted) and the in-process constructor (total limits, cross-list uniqueness), so that a malformed webhook response always follows `failurePolicy`.
- Bound union width and depth, and the webhook response size.
- Settle whether `authorization.k8s.io/v1alpha1` AuthorizationConditionsReview is served or is only a webhook wire type. The KEP and the client-go wiring disagree.
- Rewrite the KEP's SAR/ACR/config sections to match the shipped tree-shaped `conditionalDecision` and `handledDecisionTypes`.

The single most important finding: DV-valid but constructor-rejected ConditionsMaps (for example `conditionsMap: {}`) decode to NoOpinion and ignore `failurePolicy=Deny` (`encoding.go:134-142`).

### 3. Adversarial review

#### Security

**[Important] [code] An explicit or implied Deny is weakened to failurePolicy on the conditions-aware path, but not on the legacy path** -- `webhook.go:323-329`, `:349-354` vs `:262-267`.
Trace for one webhook response, by path:
1. `denied=true` plus `conditionalDecision`:
   - Legacy `Authorize` returns Deny (`:262`, tested by `TestAuthorize_FoldDown/"Denied together with an Allow-only condition stays Deny"`).
   - `ConditionsAwareAuthorize` fails validation (`authorization/validation/validation.go:117-120`) and returns
     `conditionsAwareFailureDecision`, which is **NoOpinion** under `failurePolicy: NoOpinion`.
2. An unrequested `ConditionsMap` with deny conditions when no reviewer is configured:
   - Legacy returns Deny (`FailureDecision`).
   - The conditions-aware path is rejected by `validation.go:100-103` and returns NoOpinion under failurePolicy=NoOpinion.
3. A deny-carrying map that fails DV (for example, a bad condition ID):
   - Legacy returns Deny through `conditionsmap.go:141-145`.
   - The conditions-aware path returns NoOpinion.

A NoOpinion from the webhook lets the union continue to later authorizers, for example an RBAC Allow. So the
webhook's own Deny is overridden on exactly the path that matters for conditional authz. The `failurePolicy` doc says
"malformed response → failurePolicy" (`apiserver/v1/types.go:499-507`), so this is defensible, but it contradicts
the legacy path's explicit rule (comment at `webhook.go:261`). The only test (`webhook_conditional_test.go:258-267`)
uses `decisionOnError=Deny`, so it cannot see the difference.
Fix: on a validation failure, return Deny if `status.denied` is set or the raw decision tree contains any deny
condition; otherwise use `conditionsAwareFailureDecision`.

**[Important] [code] Aggregated-API write requests are classified conditional, and the conditions are never enforced in kube-apiserver** -- `pkg/controlplane/apiserver/config.go:316-320` (#141959 code; thread #24 on this PR is unresolved).
1. `CreateAggregatorConfig` copies `kubeAPIServerConfig`, including `Authorization.ConditionalAuthorizationRequestClassifier`
   (`pkg/controlplane/apiserver/aggregator.go:64`).
2. So the outermost handler chain calls `ConditionsAwareAuthorize` for `create`/`update`/... on APIService-backed
   groups. A conditional Allow passes the filter (`filters/authorization.go:202-208`).
3. The request is then proxied to the aggregated server. kube-apiserver runs no admission for it, so the
   `AuthorizationConditionsEnforcer` never evaluates the conditions.
4. Safety relies on the aggregated server re-authorizing through delegated SAR. That SAR carries no
   `authorizationOptions`, so the webhook answers unconditionally. An aggregated server that trusts the front proxy
   and skips authz would treat the conditional decision as an unconditional Allow.

KEP `kep.md:1601-1605` requires the GVR to be "served by the current API server".
Fix: the classifier returns false for groups served by APIServices (or the proxy handler rejects a conditional ctx
decision with a 500).

**[Important] [code] Reload TOCTOU: one authorizer chain authors the conditions, and possibly a different chain evaluates them** -- `pkg/kubeapiserver/authorizer/reload.go:92-98`, filter stores the reloadable resolver at `filters/authorization.go:170`.
`ConditionsAwareAuthorize` and `EvaluateConditions` each call `r.current.Load()` independently. A reload between
the filter and the enforcer (the window covers body decode and all mutating admission) routes the union's named
sub-decisions to the new chain (`union.go:187-193`). Outcomes:
- The name was removed: fails closed.
- The name now belongs to RBAC or AlwaysAllow: `ErrorConditionEvaluationNotSupported`, then fail closed through the
  union guard.
- `conditionsReview` was removed: fails closed (`webhook.go:455-457`).
- **The same name now points at a different webhook or kubeconfig context**: the new ACR endpoint receives
  conditions it never authored. Any answer within `PossibleDecisions` is accepted, including Allow.

Not discussed in any thread.
Fix: snapshot `r.current.Load().authorizer` once per request and store that snapshot (not the resolver) in the
request context.

**[Important] [code] The delegating authorizer advertises conditional support to an endpoint that does not exist** -- `server/options/authorization.go:206`, `webhook.go:107-111`, `:287-292`; kube-apiserver serves no ACR (`pkg/registry/authorization/rest/storage_authorization.go:48-49`, v1 only).
With the gate on, every generic-apiserver delegating webhook has a non-nil reviewer, so `handlesConditional=true`.
That breaks the invariant stated at `webhook.go:285-286`. In-tree it is unreachable, because no generic server sets
a classifier (`C` §2.1 M2). But `WithConditionsAwareAuthorization` is exported. Any out-of-tree server that installs
it gets conditional decisions whose evaluation always ends in an ACR 404 and a fail-closed result. The newWithBackoff
gate check (`webhook.go:155`) is the **only** gate on this path. liggitt's thread #81 asked for both checks.
Fix: leave `AuthorizationConditionsReviewClient` nil in `toAuthorizer` until kube-apiserver serves the ACR API.

**[Question] [code] Object contents now reach the authorization webhook** -- `webhook.go:509-514`.
SAR never carried object data. The ACR now sends `object`/`oldObject` in full, including Secret `data`, to the
ACR endpoint. This is by design (KEP `kep.md:1131`, "very similar to AdmissionReview"), but neither the API docs nor
the config doc (`apiserver/v1/types.go:524-530`) mention the new data flow to authorization webhooks. Document it.

**[Nit] [code] Responses are cached before they are validated** -- `webhook.go:413-418` vs `:327`.
An invalid conditional response is cached for `authorizedTTL` and keeps failing closed for that long. A deny-only
conditional map, whose `PossibleDecisions` excludes Allow, is also cached for `authorizedTTL`.
Not a fail-open risk. Fix: cache only after validation, or use `unauthorizedTTL` unless Allow is possible.

**[Nit] [code] The ACR response read is unbounded** -- `webhook.go:812` (TODO), `:823-834`.
The same is true for SAR (pre-existing). Fix: cap the body size as admission webhooks do.

Checked and found sound:

  Legacy and conditions-aware entries therefore share a key only when `handlesConditional=false`, and then both paths

#### Bugs

**[Question] [code] An unrequested conditional answer on the legacy path gives a 500, not a 403** -- `webhook.go:264-267` → `filters/authorization.go:115-118`.
Question (a): the order is Deny-and-Allow, then Deny, then conditional, then Allow, then NoOpinion. That order is
correct: an explicit deny wins, and `allowed=true` plus a conditional never yields Allow. The returned
(Deny|NoOpinion, err) becomes a 500 only if no later authorizer allows. This matches the pre-existing handling of
webhook errors under both failurePolicies and of `allowed&&denied`. The conditions-aware filter does the same
(`filters/authorization.go:211-214`).
No exported thread discusses it (searched for "unrequested", "500", "fold"). A 500 is defensible: the webhook broke
the protocol. Record this in the KEP rather than change the code.

**[Nit] [code] The conditions-aware path validates its own outgoing spec, so it diverges from legacy** -- `webhook.go:327` → `validation.go:46-48`.

specified". Every such request then fails closed on the conditions-aware path, while legacy sends it.
Unreachable in kube-apiserver, where authn always sets a user. Fix: validate only `status` with
`ValidateSubjectAccessReviewStatus` plus the DV for status.

**[Nit] [code] Typed-nil `data` passes the nil check** -- `webhook.go:437`.

always passes a non-nil value (`conditionsenforcer.go:106-112`). Fix: reuse the `reflect` typed-nil check used for
objects.

**[Nit] [code] `result` is dereferenced without a nil check** -- `webhook.go:532`.

### 5. Verdict

The webhook part of #137633 is sound for alpha in its core protocol. An unrequested conditional answer can never
become an Allow, on either path. The conditions-aware path cannot accept a conditional decision it did not request.
`EvaluateConditions` fails closed on every error and checks the result against `PossibleDecisions`. The cache key is
complete.

Before beta, five things must change:
1. Fix the deny-weakening asymmetry between the legacy and conditions-aware failure paths.
2. Pin the request's authorizer snapshot across reloads.
3. Stop wiring delegating servers to the non-existent ACR endpoint.
4. Close the aggregated-API classification gap (owned by #141959, raised here in the unresolved thread #24).
5. Fix the vacuous UID test and the missing `allowed=true` legacy case.

The KEP must be rewritten for the config shape, the UID, the failure-decision rules and the 500 behaviour.

The single most important finding is the aggregated-API gap: conditionally allowed write requests to APIService
groups bypass kube-apiserver enforcement entirely. It is the only path where a conditional decision is never
enforced by the server that issued it, not merely enforced with surprising strictness.
