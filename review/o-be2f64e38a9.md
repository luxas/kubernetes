## What this commit does

Reshapes `UnconditionalParts()` into `UnconditionalParts(expectConditional bool)`. The new behaviour:

- If the decision is already unconditional (Allow/Deny/NoOpinion): return the triple. Same as before.
- If the decision is conditional:
  - `expectConditional == true`: fold to `FailureDecision()` with a descriptive reason mentioning the fail-closed reason.
  - `expectConditional == false`: return `FailureDecision()` with an error (`"tried to return an unexpected conditional decision during unconditional authorization"`) — this is a programmer bug.

Also reorders the switch cases to `Deny → NoOpinion → Allow` (previously `Allow → Deny → NoOpinion`), presumably for security-favouring-Deny-first ordering. Adds 163 lines of tests covering both `expectConditional` modes.

## Findings

### Important (should fix)

1. **The two modes (`expectConditional=true|false`) do very different things — this is a "boolean flag arg" that hurts readability at call sites.** `conditions.go:161`. A call like `d.UnconditionalParts(true)` gives no clue what the `true` means. Consider two named methods:
   ```go
   func (d ConditionsAwareDecision) UnconditionalPartsWithFailClosed() (Decision, string, error)  // was: expectConditional=true
   func (d ConditionsAwareDecision) StrictUnconditionalParts() (Decision, string, error)         // was: expectConditional=false
   ```
   or a small typed enum. The `bool` parameter is a smell.
2. **The reordering of switch cases (`Deny → NoOpinion → Allow`) is not documented.** `conditions.go:162–171`. The prior order was `Allow → Deny → NoOpinion`. Reordering to Deny-first mirrors the security policy of "always consider the most-restrictive answer first". Add a comment explaining the ordering choice.
3. **The failure-mode reason string is verbose:** `"failed closed from conditional decision (with possible outcomes [Allow NoOpinion]) to Deny during unconditional authorization"` (`conditions.go:172–176`). This ends up in error surfaces and audit logs. Consider a shorter form, or a `%v` on `possibleDecisions` that doesn't leak set-implementation formatting. `sets.List` returns a sorted list, so at least the ordering is stable.
4. **`expectConditional=false` case surfaces a Go-level programmer-error message to potentially external callers.** `conditions.go:182–184`: `"tried to return an unexpected conditional decision during unconditional authorization"`. This is fine for logs, but if the error escapes to a client, it's confusing. Wrap the returned `Decision` at the caller boundary with a client-safe message.
5. **`fmt.Sprintf(...)` with `sets.List(d.PossibleDecisions())` allocates on every conditional-to-unconditional fold.** `conditions.go:172–176`. Minor performance concern; probably negligible.

### Nits

- The docstring on `UnconditionalParts` (`conditions.go:158–162`) is much clearer than before. Good.
- `sets.List(d.PossibleDecisions())` returns `[]Decision`; the `%v` formats it as e.g. `[0 1]` (with integer values) which is unfriendly. Consider a small helper `formatPossibleDecisions(d.PossibleDecisions())` that maps each to its `String()`.
- Tests in `conditions_test.go` grew by 163 lines; would benefit from a test-name convention like `unconditional/allow/expect_conditional_true` vs `unconditional/allow/expect_conditional_false` for readability.

### Questions

- The `expectConditional bool` parameter — what's the actual call-site distribution? Skimming later commits: the enforcer plugin uses `expectConditional=true` (fold to failure); the SAR REST handler uses `expectConditional=true` when serializing back to the client (conditional case handled separately). If nobody uses `expectConditional=false`, remove the mode entirely.
- What guides whether a caller should use `expectConditional=true` vs `=false`? A one-liner in the docstring would help.

## What's well done

- Adding 163 lines of test coverage for the `UnconditionalParts` variants — before, only the "unconditional decision" path was exercised.
