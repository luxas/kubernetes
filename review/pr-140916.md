## 3. Adversarial review

### Security

**[Important] [code] In generic or aggregated apiservers the feature gate is the only thing that keeps conditional decisions away from `SetAuthorizer` consumers. The "advertise only when ACR is configured" safeguard does not apply there.** Locations: `staging/src/k8s.io/apiserver/pkg/server/options/authorization.go:206`, `staging/src/k8s.io/apiserver/pkg/authorization/authorizerfactory/delegating.go:60-69`, `staging/src/k8s.io/apiserver/plugin/pkg/authorizer/webhook/webhook.go:108-111,153-157,287-292`.
- The webhook advertises `handledDecisionTypes` exactly when `authorizationConditionsReviewer != nil` (`webhook.go:287`).
- kube-apiserver sets a reviewer only when `webhook.conditionsReview` is configured (`pkg/kubeapiserver/authorizer/reload.go:188-189`).
- The delegating authorizer that every generic apiserver builds sets `AuthorizationConditionsReviewClient: client.AuthorizationV1alpha1()` unconditionally (`options/authorization.go:206`). `NewFromInterface` turns that into a reviewer (`webhook.go:109-111`), and the only filter is the gate (`webhook.go:155-157`).

So with the gate on in both the aggregated server and kube-apiserver, an out-of-tree plugin in the aggregated server that calls `ConditionsAwareAuthorize` on the authorizer from `SetAuthorizer` can receive a `ConditionsMap` or `Union` relayed through kube-apiserver's SAR. Its `EvaluateConditions` then posts an `AuthorizationConditionsReview` to kube-apiserver, which serves only `authorization.k8s.io/v1` (`pkg/registry/authorization/rest/storage_authorization.go:47-49`). That call always errors and fails closed. A plugin that skips evaluation and tests `!d.IsDeny()` or `d.PossibleDecisions().Has(Allow)` fails open instead.

This matters because aggregated apiservers built on `k8s.io/apiserver` are where out-of-tree admission plugins actually live. They are the population this PR restored `WantsAuthorizer` for: kube-apiserver cannot load out-of-tree plugins without a fork. In-process plugins are trusted code, so this is a misuse hazard, not an attacker path. That, plus the alpha gate, is why it is Important rather than Critical. It overlaps Q6.

Suggested fix: do not pass the v1alpha1 client by default in `options/authorization.go:206` (make it an explicit opt-in). Also state on `WantsAuthorizer` that a `ConditionsAwareAuthorize` result must go through `EvaluateConditions` or `UnconditionalPartsOrFailClosed`.

**[Question] [code] With the gate off, the server `Authorizer` handed to `SetAuthorizer` never returns a conditional decision. That holds, but only through a chain of four separate facts.**
1. Without the gate, the reviewer is dropped (`webhook.go:153-157`), so `handlesConditional=false` (`:287`).
2. A response carrying `conditionalDecision` is then `Forbidden` (`staging/src/k8s.io/apiserver/pkg/apis/authorization/validation/validation.go:98-102`), and `conditionsAwareFailureDecision` returns an unconditional NoOpinion or Deny (`webhook.go:349-354`).
3. Every other authorizer lifts via `FromParts`.
4. The union folds when the possible decisions are a singleton (`conditionsunion.go:144`).

The webhook leaf is tested (`webhook_conditional_test.go:TestConditionsAwareAuthorize/"no reviewer, unrequested conditional decision fails closed"`, `:324`). The composed property at the `SetAuthorizer` boundary is not. Separately, even with the gate off, the webhook's `ConditionsAwareAuthorize` is not output-equivalent to its `Authorize`:
- it validates the SAR response (`webhook.go:327-329`), which `Authorize` does not (`:241-270`);
- it attaches `status.evaluationError` as an error (`:331-344`).

A 1.36 plugin that migrates from `Authorize` to `ConditionsAwareAuthorize` therefore sees new errors with the gate off. Is this intended? It is #137633's area; it is recorded here because `WantsAuthorizer` is the door through which out-of-tree code reaches it.

**[Nit] [code] "Narrower" is a static type, not a capability boundary** (`init/initializer.go:95`, `init/interfaces.go:46`). `SetUnconditionalAuthorizer` now receives the full `Authorizer` value, so any `WantsUnconditionalAuthorizer` plugin can type-assert to `authorizer.Authorizer` and call `ConditionsAwareAuthorize`. Before this PR the stored value was also the full object (the field type was static only), so nothing regressed. No in-tree plugin does this: `grep '\.(authorizer\.Authorizer)'` over non-test `staging/.../apiserver`, `plugin` and `pkg` is empty. Fix: say "narrower interface type" in the doc so it does not read as an enforcement boundary.

Also checked, nothing found:
- **Nil handling.** A nil `Authorizer` passed to `New` converts to a nil `UnconditionalAuthorizer` interface, so `== nil` checks in `ValidateInitialization` still fire (`plugin/pkg/admission/gc/gc_admission.go:305`, `plugin/pkg/admission/noderestriction/admission.go:151,156`, `.../policy/generic/plugin.go:227`).
- **The conditions enforcer** gets its authorizer from the request context (`.../conditionsenforcer/conditionsenforcer.go:84`), not from either initializer hook, so this PR cannot change which authorizer evaluates the request's conditions.
- **Caches, CEL, logs, SAR, impersonation:** none touched by this PR.

### Bugs

**[Nit] [code] Order when a plugin implements both interfaces is fixed but undocumented** (`init/initializer.go:94-99`). Each setter is called exactly once, `SetUnconditionalAuthorizer` first, with the same value. There is no duplication defect: for a plugin that stores the value, the second call is idempotent. The order is observable only if a setter has side effects, such as wrapping or caching the authorizer, or `ValidateInitialization` depending on which setter ran last. No in-tree plugin implements both. Fix: document "both are called, Unconditional first, same value" on `Initialize`.

## 5. Verdict

The merged code is sound for alpha. It is a faithful, minimal restoration of the 1.36 Go API, it has no runtime effect on in-tree binaries, and both setters receiving the same value is harmless.

What it exposes is a contract gap. `WantsAuthorizer` hands third-party in-process code the full conditions-aware `Authorizer`, and the only things keeping that code fail-closed are the feature gate and the plugin author's own handling. Neither the interface doc nor the KEP says what such a caller must do. Before beta:
- document the obligation on `WantsAuthorizer` and in the KEP;
- add the dual-interface and identity tests;
- settle the generic-apiserver case.

The single most important finding: generic and aggregated apiservers, where out-of-tree admission plugins live, always advertise conditional support to kube-apiserver once the gate is on (`options/authorization.go:206`). The "only advertise when ACR is configured" safeguard therefore does not protect `SetAuthorizer` consumers there; conditional decisions reach them that can never be evaluated successfully.
