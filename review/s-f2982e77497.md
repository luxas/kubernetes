## What this commit does

Extends the CEL environment used by `AuthorizationConfiguration.Authorizers[].MatchConditions` (the operator-facing CEL for filtering which authorizers see a given request) to include the new `SubjectAccessReviewSpec.authorizationOptions` field, gated by the `ConditionalAuthorization` feature gate.

Two places changed:
- `buildRequestType` (`compile.go:207–223`) — adds an `authorizationOptions` field to the SAR spec DeclType.
- `convertObjectToUnstructured` (`compile.go:341+`) — populates the `authorizationOptions.handledDecisionTypes` slice into the CEL evaluation input, gated by the same feature gate.
- Test file (`compile_test.go`) — enables the feature gate for `TestBuildRequestType`.

## Findings

### Critical (must fix before merge)

None.

### Important (should fix)

1. **This extension is to the *matcher* CEL environment (for `AuthorizationConfiguration.Authorizers[].MatchConditions`), not to a "condition evaluator" CEL env for the new `type: k8s.io/authorization-cel` conditions.** The commit message could be clearer: "Extend the AuthorizationConfig match-conditions CEL env with the new `authorizationOptions` SAR field, so operators can write matchConditions like `request.authorizationOptions.handledDecisionTypes.exists(t, t == "ConditionsMap")`." Update the KEP if it isn't already precise about this distinction.
2. **`handledDecisionTypes` is cast from `[]ConditionsAwareDecisionType` to `[]string` in `convertObjectToUnstructured`.** `compile.go:346–351`. This drops the type information — CEL match expressions comparing to a specific string literal like `"ConditionsMap"` will work, but there's no compile-time protection against typos (`"ConditionsMapp"`). Consider whether CEL enum support could enforce the closed set.
3. **The DeclType `field("handledDecisionTypes", apiservercel.NewListType(apiservercel.StringType, -1), true)` uses `required=true`, but the field is optional on the wire (via `omitempty` on `AuthorizationOptions.HandledDecisionTypes` — wait, it's actually `+required` on the wire).** Verify the CEL required flag matches the wire's `+required` marker. If not, mismatched required-ness could make match-conditions crash on unset input.

### Nits

- `buildAuthorizationOptionsType` (`compile.go:227–231`) is a two-line helper that builds a single-field object. Inline unless it's expected to grow later.
- The feature-gate wrapping is consistent between `buildRequestType` and `convertObjectToUnstructured` — good; a gate-off SAR shouldn't expose the new field at all.
- The test file adds `nativeTypeToCELType` cases for `*v1.AuthorizationOptions` and `[]v1.ConditionsAwareDecisionType` — nice, keeps the mirror-testing pattern working.

### Questions

- If an operator writes a match-condition that references `request.authorizationOptions.handledDecisionTypes` but a client sends a SAR without `authorizationOptions`, does the CEL evaluation error out with "unknown field" or gracefully treat it as null? Test suggests it treats as null (via the `if obj.AuthorizationOptions != nil` guard at conversion time).

## What's well done

- Feature-gate wrapping in both the type definition and the object conversion means the CEL surface doesn't lie about what's available when the gate is off. Consistency reduces operator confusion.
- Test enables the feature gate during test to exercise the new code path — the right pattern.
- The added `nativeTypeToCELType` case for `[]v1.ConditionsAwareDecisionType` explicitly maps to `NewListType(StringType, -1)`, so if the enum ever grows type-safety, the mapping is a single point of update.
