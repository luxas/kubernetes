## What this commit does

Wires the three SAR REST handlers (`local`, `self`, `subjectaccessreview`) to produce conditional decisions when the feature gate is on **and** the client has opted in via `spec.authorizationOptions.handledDecisionTypes`. Three-way branch:

1. FG on + client supports conditions → call `authz.ConditionsAwareAuthorize`, serialize the resulting `ConditionsAwareDecision` into `status.conditionalDecision` (or `status.allowed`/`status.denied` if the decision folded to unconditional).
2. FG off, or client only supports unconditional → call classic `authz.Authorize`, encode as before.
3. Client's `HandledDecisionTypes` is neither set → 400 Bad Request.

Also:
- Widens `NewREST`/`REST.authorizer` from `UnconditionalAuthorizer` to `Authorizer` (correct — SAR is now conditions-aware).
- Clears any client-supplied `status` before validation (defensive; the client should never populate status, but the server was permissive before this commit; hardening now is fine).
- Clears `AuthorizationOptions` when FG is off (belt-and-suspenders — the authorizer still shouldn't return conditions when the FG is off, but this ensures the request looks conditions-unaware to the code path).
- New encoding helper: `apiserverauthorizationv1.SerializeConditionsAwareDecision` in `staging/src/k8s.io/apiserver/pkg/apis/authorization/v1/encoding.go` — the internal `ConditionsAwareDecision` → wire form.
- Helper `authorizationutil.ConditionsAwareDecisionToSARStatus` — the SAR-specific mapping including the "fold unconditional into top-level status.allowed/denied" logic.

## Findings

### Critical (must fix before merge)

1. **Nil-panic potential on `subjectAccessReviewV1.Spec.AuthorizationOptions.SupportsConditionalAuthorization()`.** `rest.go:109`. `AuthorizationOptions` is a pointer. When it's nil (which is the default for legacy clients), `SupportsConditionalAuthorization()` is called on a nil receiver. Looking at `util.go:42–45` (from the previous commit): the method dereferences `ao.GetHandledDecisionTypes()`, which handles nil by returning the unconditional set. So the nil case is *safe* — but the reader can't tell from the call site. Add an explicit nil check or move to `subjectAccessReviewV1.Spec.AuthorizationOptions.GetHandledDecisionTypes()` (already nil-safe).
2. **The FG-off code path clears `subjectAccessReview.Spec.AuthorizationOptions = nil` before validation** (`rest.go:80–82`). This means the field is silently ignored — a client that carefully sets `handledDecisionTypes=[Allow, Deny, NoOpinion, ConditionsMap, Union]` won't get an error; they get a stripped request. Consider whether this should be a warning header (`Warning: ConditionalAuthorization feature gate is disabled; authorizationOptions.handledDecisionTypes ignored`) to help the operator diagnose "why am I not getting conditions?"

### Important (should fix)

1. **The three-way branch is subtly asymmetric.** `rest.go:107–125`:
   - Branch 1: FG on + `SupportsConditionalAuthorization` → conditions path.
   - Branch 2: `SupportsUnconditionalAuthorization` (regardless of FG state or the FG being on but only-unconditional-supported) → classic path.
   - Branch 3: neither → 400.
   The reader must think about which combinations end up in Branch 2 vs. Branch 1. If a client sends only `[Allow, Deny, NoOpinion]` and FG is on, we go Branch 2 (classic) — that's the correct fold. But rewrite the switch order for clarity: check `SupportsUnconditionalAuthorization` first (the minimum contract), then check `SupportsConditionalAuthorization`, then dispatch based on FG.
2. **`ConditionsAwareDecisionToSARStatus` handles conversion failure by returning `Denied=true`.** `helpers.go:270–276`. The comment says "This conversion should never fail" — that's likely true for well-formed internal decisions, but treating conversion failure as `Denied` is a fail-closed choice. Verify that no legitimate decision can fail to convert (fuzz-test the conversion pathway).
3. **Response payload potentially leaks internal-form errors.** `helpers.go:274` — `EvaluationError: BuildEvaluationError(err, attrs)`. The `err` here is a scheme conversion error message; verify it doesn't include the raw decision struct in `%v` form.
4. **The 597-line rest_test.go grew presumably to cover both the conditions and unconditions branches.** Verify:
   - FG off + conditional client → classic path.
   - FG on + non-conditional client → classic path.
   - FG on + conditional client → conditional path.
   - FG on + conditional client + authorizer returns unconditional → status.allowed/denied populated, not `conditionalDecision`.
   - FG on + conditional client + authorizer returns ConditionsMap → `status.conditionalDecision` populated.
   - FG on + conditional client + authorizer returns Union → tree preserved.
   - Client sends `HandledDecisionTypes = []` → 400.
5. **`storage_authorization.go` change is 1 line (verify).** Probably the `NewREST` calls now pass the full `Authorizer` — sanity check.

### Nits

- `helpers.go:245` — function name mismatch in the comment: `SARStatusFromAuthorize` vs. actual name `ConditionsAwareDecisionToSARStatus`. Fix.
- The `Clear status so it's not taken into account during input validation` comment (`rest.go:73–75`) explains a subtle defense; keep it.
- `rest.go:80–82` — the "clear when FG off" defense — good, but the comment could point at Branch 2's fall-through so it's obvious why this matters.

### Questions

- The three SAR REST handlers (`local`, `self`, `subjectaccessreview`) all get near-identical treatment. Any reason not to consolidate the conditions-aware branching into a shared helper?
- `SelfSubjectAccessReview` — does it support conditions? Since the whole point of SelfSAR is "tell me what I can do", conditions are exactly the extra information users want. Verify Branch 1 works for SelfSAR too.

## What's well done

- The FG-off code path is not merely "no-op"; it clears the client's options so the classic path handles the request cleanly. Defensive.
- The 400 for unrecognized `HandledDecisionTypes` prevents silent misuse — the client either declares support for the classic set or the conditions set, not something in between.
- The encoding helper `SerializeConditionsAwareDecision` correctly translates the internal decision to the wire form; separate serialize/deserialize logic keeps the pattern testable in isolation.
- 143-line `encoding_test.go` — comprehensive round-trip coverage.

## Verdict

**LGTM with nits.** The core logic is correct, the wire-form serialization is in the right place. Critical items are documentation/defensiveness improvements.
