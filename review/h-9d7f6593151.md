## Findings

### Critical (must fix before merge)

1. **Constructor accepts a `nil` `Condition` in a slice without validation until much later.** `conditionsmap.go:135–140` (`validateConditions`) dereferences `condition.GetID()`. If any element of `denyConditions`/`noOpinionConditions`/`allowConditions` is `nil`, this will panic — not the "fail closed" behaviour the constructor otherwise practices. The docstring on `ConditionsAwareDecisionConditionsMap` (`conditionsmap.go:112`) says "All conditions must be non-nil, this function panics if any condition is nil." — but the actual behaviour is to panic on the first `nil.GetID()` call, which is arguably not the caller's fault. Prefer a check like:
   ```go
   for _, c := range slices.Concat(denyConditions, noOpinionConditions, allowConditions) {
       if c == nil {
           return makeFailClosedError(fmt.Errorf("condition must not be nil"))
       }
   }
   ```
   Making this a fail-closed decision, not a panic, keeps parity with the other error paths in this constructor.

### Important (should fix)

1. **Missing byte-length validation on `Condition.Condition` and `Condition.Description`.** The KEP prescribes 10240 / 1024 byte caps (`MaxConditionBytes` / `MaxConditionDescriptionBytes`), but this commit only checks `ID` and `Type` are label keys. Those constants are added later in `3033213ea26`. If this commit ships without them, an authorizer can hand out a 10-MB condition body — DoS vector against a downstream `AuthorizationConditionsReview` webhook and audit logs.
2. **`GenericCondition` is missing the `EvaluateFunc` field described in later docs.** `conditionsmap.go:210–224`. At HEAD, `GenericCondition` has no `EvaluateFunc` because the `Evaluate` method isn't part of the `Condition` interface yet (added in `666dea045e8`). Add a `TODO(next commit): add EvaluateFunc` to guide the reader.
3. **`String()` output for `ConditionsMap` variant leaks the counts.** `conditions.go:221–232`. The format `ConditionsMap(denies=N, noopinions=N, allows=N)` is fine but note that this output ends up in error messages and audit logs. Consider whether the count of Deny conditions is information that reveals internal authorizer structure. Probably fine, but flag for security review.
4. **`ConditionsMap.PossibleDecisions()` doesn't consider NoOpinion in the "must include" set.** `conditionsmap.go:99–107`. Starts with `sets.New(DecisionNoOpinion)` then adds `Allow`/`Deny` if their slices are non-empty. This is correct — NoOpinion is *always* a possible outcome. Great. But there's an edge case: what if the map has *only* NoOpinion conditions? The constructor (line 128) short-circuits to `ConditionsAwareDecisionNoOpinion` in that case, so the map is never constructed. Good — but this invariant is only enforced by the constructor. If someone constructs a `ConditionsMap` value directly via zero-value struct literal, the invariant is violated. Since `ConditionsMap` has only private fields, external code can't construct one — but if reflection or unsafe.Pointer sneaks by, this is a latent trap. Consider a constructor-only pattern with a `sealed struct{}` field.
5. **`validateConditions` uses `strings.Join(errs, "; ")` on the error slice from `IsLabelKey`.** `conditionsmap.go:157–159`. `IsLabelKey` returns `[]string`, but the join with `"; "` gives you `"a; b; c"`; if any of the errors contain semicolons, this becomes lossy. Minor. Use `errors.Join` if the return type is `[]error`, but here it's `[]string` so this is fine.

### Nits

- `conditionsmap.go:30–32` — the invariant comment is helpful:
  `// invariant: len(denyConditions) != 0 || len(allowConditions) != 0`
  Consider adding a second invariant: `// invariant: total count of conditions <= MaxConditionsPerMap`.
- `conditionsmap.go:47–51` — `FailureDecision` on `ConditionsMap` is duplicated with the one on `ConditionsAwareDecision`. Keep in sync manually or refactor into a shared helper.
- `interfaces.go:290–296` — `AdmissionOperation` is a `string` alias. Consider whether it should be typed distinctly from `admission.Operation` to catch mis-conversions at the type checker. Currently `AdmissionOperation` and `admission.Operation` are both string aliases; casting between them is silent.
- `conditions.go:157–158` — the `case d.IsConditionsMap(): return d.ConditionsMap().PossibleDecisions()` in the `PossibleDecisions` switch fixes the landmine flagged in review of `98eab691156`. Good.
- `conditionsmap.go:63,74,85` — three near-identical `iter.Seq[Condition]` accessors. Consider generating them or accepting a single `Effect string` argument. Reads fine as-is, though.

### Questions

- The `runtime.Object` / `schema.GroupVersionResource` / `user.Info` imports in `interfaces.go` are new dependencies for the `authorizer` package. Verify no circular dependencies introduced (e.g. does `runtime` import from `authorizer`?). Spot check: no.
- Is there a reason `Condition` is an interface rather than a struct? The KEP explanation is compact reasoning about pre-compiled representations for in-process evaluation. Since `Evaluate` isn't on the interface yet (added next commit), this commit's `Condition` interface is a struct-in-drag. Confirm intent.
- The one-line change in `pkg/admission/interfaces.go` — what did it do? Prosely inspect.

## What's well done

- The constructor is exemplary: fail-closed on invalid input by returning a `ConditionsAwareDecision` that carries the error, rather than panicking or returning a nil-check error. This is the right pattern for security-critical code paths.
- The immutability guarantee via `slices.Clone` on all three input slices (`conditionsmap.go:174–177`) is the right defensive move — otherwise a caller could mutate its slice after handing it over.
- The iterator-based accessors (`iter.Seq[Condition]`) are idiomatic Go 1.23+ and force callers to think about iteration rather than fetching indices.
- `PossibleDecisions()` on `ConditionsMap` is correct and clean.
- The short-circuit at `conditionsmap.go:129–131` folds "only NoOpinion conditions" into a plain `NoOpinion` decision — good, keeps the invariant clean.
