## What this commit does

Adds `conditionalRequestClassifier` in `pkg/controlplane/apiserver/config.go` and wires it into `genericConfig.Authorization.ConditionalAuthorizationRequestClassifier` when the `ConditionalAuthorization` feature gate is on. The classifier returns `true` for a request when *all* of:

- Resource is concrete (not empty, not `*`).
- API group is not `*`.
- API version is concrete (not empty, not `*`).
- The GroupResource is not on the admission `exclusion.Excluded()` list.
- Verb is one of `create`, `update`, `patch`, `delete`, `deletecollection`.

Includes a 181-line test file that covers each rejection branch and the happy path. Also a small update to `staging/src/k8s.io/apiserver/pkg/server/config.go` (+9) — probably the field wiring itself.

## Findings

### Critical (must fix before merge)

None. The classifier is conservative — anything that doesn't fit the write-verb + concrete-GVR + not-excluded pattern returns `false`, so the conditions-aware code path is not activated. Failure mode: legitimate requests fall through to `WithAuthorization`, which is exactly the safe behaviour.

### Important (should fix)

1. **TODO comments in the classifier body list two important follow-ups that are not yet in this branch.** `config.go:315–319`:
   ```
   // TODO(luxas): Inspect whether the API group belongs to an aggregated API server, and in that case,
   // always consider the request to be conditions-aware, as the aggregated API server could support
   // conditions for any kind of request.
   // Also, support connect requests that are accessed through the GET HTTP verb.
   ```
   Both are important gaps:
   - Aggregated API servers currently don't get conditional authz support because the classifier rejects any request the kube-apiserver doesn't own. This blocks the KEP's aggregated-API-server story.
   - Connect requests (pods/exec, pods/attach, pods/portforward, nodes/proxy) via the GET verb are rejected. This is the KEP's compound-authz-for-connectible-resources story — a major use case.
   File follow-up issues for both.
2. **The classifier's contract is "returns true iff the enforcer plugin will fire".** But the plugin is registered separately (`AllOrderedPlugins`) and is *only enabled* when the FG is on. If somebody disables the plugin explicitly (say via `--disable-admission-plugins=AuthorizationConditionsEnforcer`), the classifier still returns `true` for eligible requests → conditional decisions get attached to the context, and nothing enforces them → **fail-open**. Cross-reference with the plugin-registration in commit 20 (`67896e14ab4`) — the plugin-enabled flag is checked in the HTTP filter, not in the classifier. Verify this end-to-end.
3. **`admissionVerbs = sets.New("create", "update", "patch", "delete", "deletecollection")` uses strings.** `config.go:294`. Verify no accidental mismatch with the verb strings emitted by `RequestInfo.Verb` — these are typically lowercase; confirm by inspection.

### Nits

- The classifier is a top-level function in `pkg/controlplane/apiserver/config.go` — consider naming `conditionalRequestClassifier` → `kubeAPIServerConditionalAuthzClassifier` to signal it's the kube-apiserver-specific implementation. Aggregated API servers will need their own classifiers eventually.
- The comment `// If the verb is one which is subject to admission, the ConditionsEnforcer will catch the request, and thus is the request conditions-aware.` is a good rationale statement.
- Test coverage is comprehensive: empty/wildcard for each field, excluded GR, non-admission verbs, positive case. Good.

### Questions

- The `slices.Contains(exclusion.Excluded(), gr)` check — is this O(n) on every request? The `Excluded()` list is small (a handful of well-known GRs like `events.k8s.io/events`), so it should be fine. But if the list grows, consider `sets.New(exclusion.Excluded()...)` for O(1) lookup.

## What's well done

- The classifier is conservative and error-resistant: any missing/wildcard field returns `false`, which is the safe fallback.
- The 181-line test coverage exercises every branch — great.
- Wiring is contained inside a feature-gate check (`utilfeature.DefaultFeatureGate.Enabled(...)`), so the classifier is only installed when the FG is on.

## Tests

### Test files touched

### Coverage
- **Well covered:**
  - Empty resource → false.
  - Wildcard resource → false.
  - Wildcard API group → false.
  - Empty API version → false.
  - Wildcard API version → false.
  - Excluded GroupResource → false.
  - Non-admission verb (get, list, watch) → false.
  - Positive case: `create`/`update`/`patch`/`delete`/`deletecollection` with concrete GVR not on the exclusion list → true.
- **Missing / thin:**
  - **`connect` verb** (a TODO in the classifier): `pods/exec`, `pods/attach`, `pods/portforward` — no test row. If the TODO is intentionally not-yet-implemented, a `t.Run("connect_verb_rejected_pending_todo", ...)` documenting the current behaviour would be useful.
  - **Aggregated-API-server groups** (also a TODO): no test row.
  - **Custom `exclusion.Excluded()` list**: the test picks the first entry; if the exclusion list is empty, `t.Fatal("expected at least one excluded resource")` fires — brittle. Consider using a test-scoped exclusion list rather than depending on the global.
  - **`slices.Contains(exclusion.Excluded(), gr)` performance**: no benchmark. If the exclusion list ever grows, this becomes a per-request O(n) cost — worth a `BenchmarkConditionalRequestClassifier`.
- **Feature-gate on/off:** the classifier is installed by `BuildGenericConfig` only when the FG is on. Neither the on-nor-off installation state is tested at the wiring level; only the classifier function itself is tested.

### Structure
- Table-driven test — clean.
- Consider `t.Parallel()` in the subtest — the tests are pure functions of `attrs`, so parallel is safe.
