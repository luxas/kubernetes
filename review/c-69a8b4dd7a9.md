## What this commit does

Adds the two new required methods (`ConditionsAwareAuthorize`, `EvaluateConditions`) to every in-tree `Authorizer` implementation so the tree still compiles after `6d78dfd60cf` grew the interface. In every non-conditions-aware authorizer the pattern is identical: `ConditionsAwareAuthorize` delegates via `ConditionsAwareDecisionFromParts(self.Authorize(...))`, and `EvaluateConditions` returns `(DecisionDeny, "", ErrorConditionEvaluationNotSupported)`. The `instrumentedAuthorizer` (metrics wrapper) is genuinely extended — it counts conditional decisions as a new `"conditional"` metric label. The `union` authorizer's element type widens from `UnconditionalAuthorizer` back to `Authorizer` (undoing part of commit 02) — expected, because a union must be conditions-aware if any of its members is.

## Findings

### Critical (must fix before merge)

None. The migration is mechanical and the fail-closed behaviour in `EvaluateConditions` (return `DecisionDeny, "", ErrorConditionEvaluationNotSupported`) is exactly what the interface docstring in commit 01 prescribed.

### Important (should fix)

1. **`unionAuthzHandler.EvaluateConditions` fail-closes to Deny, but a union that contains no conditions-aware members should arguably never be called for evaluation at all.** `staging/src/k8s.io/apiserver/pkg/authorization/union/union.go:80–82`. Since this function is called by the enforcer plugin only when the request context contains a conditional decision, and since a union that never returned conditions cannot produce such a context entry, this method is unreachable in practice — but returning `DecisionDeny` with `ErrorConditionEvaluationNotSupported` here means that if a member sub-authorizer *does* return conditions and the union forwards them, this method still fails closed. That's inconsistent with the eventual union semantics landed in later commits (`d725c326bcd` reworks the union). Not a bug in this commit, but the interim state is confusing. Consider adding a comment: `// This method is only reached when the union has been superseded by the conditions-aware union in a later commit; kept for compilation.`
2. **`InstrumentedAuthorizer` widening loses no information but changes semantics for callers.** `staging/src/k8s.io/apiserver/pkg/authorization/metrics/metrics.go:62–75`. Previously took `UnconditionalAuthorizer`; now takes `Authorizer`. Any caller that supplied a bare `UnconditionalAuthorizer` will now fail to compile. Given all in-tree call sites are being updated in this commit, that's fine — but flag for external callers if any exist.
3. **`instrumentedAuthorizer.ConditionsAwareAuthorize` uses `"conditional"` as the label value for ConditionsMap/Union decisions.** `metrics.go:110–115`. The label vocabulary `{allowed, denied, conditional}` matches the SAR status field names for the first two but "conditional" is coined here. Verify against the metrics naming conventions in `kep.md` — the KEP earlier proposed `authorization.k8s.io/is-conditional-decision` as the audit annotation; the metrics label should mirror that either as `"conditional-decision"` or `"conditional"` consistently across the codebase.
4. **`instrumentedAuthorizer.EvaluateConditions` records `"unknown"` on any unexpected `Decision` value.** `metrics.go:126–129`. This is fine, but the `Decision int` enum has three known values; the default case is defensive but bumps a metric labeled `"unknown"` that operators might alert on. Consider whether it should be a `klog.Warningf` + panic in the default branch instead (this is authenticated code that should have a closed value set).
5. **Missing test for `EvaluateConditions` fail-closed path.** All the added implementations (`abac`, `node`, `rbac`, `unionAuthzHandler`, `PolicyList`) have new `EvaluateConditions` methods returning the sentinel error — but the tests table doesn't include even one assertion that calling `EvaluateConditions` on these types returns `ErrorConditionEvaluationNotSupported`. If a future refactor accidentally returns `DecisionAllow`, tests would not catch it.
