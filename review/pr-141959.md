## 3. Adversarial review

### Security

**[Important] [code] Requests to aggregated APIs are classified conditions-capable, but kube-apiserver never enforces their conditions.** `pkg/controlplane/apiserver/config.go:299-321`; `staging/src/k8s.io/kube-aggregator/pkg/apiserver/handler_proxy.go:107`; contract at `staging/src/k8s.io/apiserver/pkg/endpoints/filters/authorization.go:53-54`.
- The classifier has no "served locally" check. The aggregator copies the kube-apiserver config, classifier included (`pkg/controlplane/apiserver/aggregator.go:64`). A `create`/`update`/`patch`/`delete`/`deletecollection` on an APIService-backed group therefore gets `ConditionsAwareAuthorize`. A conditional allow passes the filter (`authorization.go:202-208`), and the proxy forwards the request with no admission in kube-apiserver.
- Enforcement then depends entirely on the aggregated server re-authorizing. Its delegated SAR uses `Authorize` with no `authorizationOptions`, so a conforming webhook answers unconditionally and the result fails closed. An aggregated server that does no authorization of its own (a supported 1.37 configuration, which relied on kube-apiserver's decision being final) executes a request whose conditions may evaluate to Deny.
- This breaks the classifier's own "MUST guarantee enforcement" contract. The TODO at `config.go:314-317` proposes classifying *more* aggregated requests (all verbs) as conditional, which would widen the hole.
- Why it matters: a fail-open path the moment the gate is enabled, invisible to the aggregated server's operator.
- Fix: return false from the classifier when the GroupVersion is served by a non-local APIService (the aggregator knows), or have the proxy handler 403 any request whose ctx decision is not `IsAllow()`.

**[Important] [code] An unsafe corrupt-object delete skips admission, so a conditional `delete` becomes unconditional.** `staging/src/k8s.io/apiserver/pkg/endpoints/handlers/delete.go:141-163,169`; `staging/src/k8s.io/apiserver/pkg/registry/generic/registry/corrupt_obj_deleter.go:111,134` (`rest.ValidateAllObjectFunc`).
- With `AllowUnsafeMalformedObjectDeletion` (Beta, default on since 1.37, `pkg/features/kube_features.go:2142-2145`) and `ignoreStoreReadErrorWithClusterBreakingPotential: true`, the handler checks only an unconditional `unsafe-delete-ignore-read-errors` permission (`delete.go:157`, `:357-390`). It then deletes without calling `deleteValidation`, so the enforcer never runs.
- A user holding a conditional `delete` plus an unconditional `unsafe-delete-ignore-read-errors` deletes with the conditions unevaluated. The classifier cannot see delete options, so the classifier cannot fix this.
- Why it matters: a fail-open path in a default-on 1.37 feature. Conditions cannot be evaluated on an undecodable object anyway, so the correct answer is to refuse.
- Fix: in `DeleteResource`, when the unsafe option is set, reject with 403 unless the ctx decision `IsAllow()`.

**[Important] [code/KEP] Mutating admission, all built-in validators and VAP run before authorization is final, including their side effects and messages.** `pkg/kubeapiserver/options/plugins.go:73-117` (the enforcer is at position 37 of 40, `:114`); `plugin/pkg/admission/namespace/autoprovision/admission.go:65-95`.
- `NamespaceAutoProvision` creates a Namespace inside `Admit`. Its own comment says "if we're here … we're allowed to do what we're trying to do" (`:65`). With conditional authorization a user whose conditions evaluate to Deny can still cause namespaces to be created.
- Mutating webhooks with side effects (`sideEffects: Some`) are called for requests that end up denied.
- Validating plugins earlier in the list (PodSecurity, NodeRestriction, CertificateApproval/Signing, OwnerReferencesPermissionEnforcement, EventRateLimit, …) and VAP run first. Their rejection messages, which can include `messageExpression` output over params or the object, are returned to a caller who is not authorized.
- In 1.37 none of these ran for an unauthorized request. The KEP accepts "fully-mutated object" (`kep.md:974-975`) but never discusses side effects, and states the enforcer is the *first* validating plugin (`kep.md:977-979`).
- Why it matters: it changes a long-standing invariant ("admission only sees authorized requests") that in-tree plugins and webhooks rely on.
- Fix: document the invariant change in the KEP. Make `NamespaceAutoProvision` (and any side-effecting in-tree plugin) skip when the ctx decision is not `IsAllow()`. Reconsider placing the enforcer before built-in validators and VAP.

**[Important] [KEP] SAR and LocalSAR return another user's full conditions tree, and the webhook cannot know who is asking.** `pkg/registry/authorization/localsubjectaccessreview/rest.go:109-111`, `subjectaccessreview/rest.go:100-102`, `util/helpers.go:276`.
- The SAR the webhook receives describes the subject, not the requester, so a webhook cannot follow the KEP's advice to hide sensitive conditions from some callers (`kep.md:2008-2011`).
- The KEP's risk analysis covers only SelfSAR (`kep.md:1995-2011`).
- Who can read other users' trees:
  - LocalSAR create is granted to every namespace admin by default (`plugin/pkg/auth/authorizer/rbac/bootstrappolicy/policy.go:421`). Namespace admins can read every user's condition expressions, IDs and descriptions for their namespace.
  - Cluster SAR create is in the node authorizer's static rules (`policy.go:216`, wired at `pkg/kubeapiserver/authorizer/config.go:122`). Any kubelet credential can read any user's conditions cluster-wide.
- Why it matters: condition expressions are policy source code. This is a new disclosure channel beyond the 1.37 allowed/denied/reason.
- Fix: the KEP must state the SAR/LSAR exposure explicitly. Consider returning the folded status (never `conditionalDecision`) unless the subject equals the requester, or gate it behind a separate verb.

**[Important] [code] The filter and the enforcer read the feature gate from different sources; if they disagree, requests pass unenforced.** `staging/src/k8s.io/apiserver/pkg/server/config.go:1077` (`utilfeature.DefaultFeatureGate`) vs `conditionsenforcer.go:63-65,74-76` (gate injected via `InspectFeatureGates`).
- If a server sets a classifier and passes `Admission.ApplyTo` a FeatureGate with the gate off while `DefaultFeatureGate` has it on, the conditions-aware filter is installed (`ConditionsEnforcerPluginEnabled` checks only the plugin *name*, `server/options/admission.go:183`) while the enforcer's `Handles()` is false. Conditionally allowed requests then complete unenforced.
- In-tree this is unreachable, because kube-apiserver passes `DefaultFeatureGate` (`pkg/controlplane/apiserver/config.go:434`). `RecommendedOptions` explicitly invites a custom `FeatureGate` (`staging/src/k8s.io/apiserver/pkg/server/options/recommended.go:73`).
- Why it matters: a latent fail-open in exported generic wiring.
- Fix: decide filter selection from the same gate the enforcer saw (for example, admission ApplyTo records `featureGate.Enabled(...) && pluginEnabled`), or make the enforcer reject when the ctx holds a conditional decision even if its own gate is off.

**[Question] [code/KEP] The ctx stores the *reloadable* authorizer, so a reload between authorization and admission changes who evaluates the conditions.** `authorization.go:170` stores `a` = `reloadableAuthorizerResolver`; `pkg/kubeapiserver/authorizer/reload.go:96-98` evaluates against `r.current.Load()`; `staging/src/k8s.io/apiserver/pkg/authorization/union/union.go:198-203` dispatches by name.
- Conditions minted by configuration N are evaluated by configuration N+1. A renamed or removed authorizer fails closed. A different webhook reusing the same name receives conditions it never issued.
- The KEP claims the two stages are atomic (`kep.md:533-537`).
- Fix: store a snapshot of the current union in the ctx (cheap: one atomic load at filter time).

**[Nit] [code] SelfSAR exposes the configured authorizer names and chain structure to any user.** `helpers.go:276`; asserted in `conditionalauthorization_test.go:1076-1101` (`system-privileged-group…`, `conditional-webhook`, `rbac`). This is low-value topology disclosure. Fix: document it, or redact NoOpinion leaves without reasons.

**[Nit] [code] Some DELETEs complete without evaluating conditions and return the object.** The namespace re-delete with finalizers returns the namespace without calling `deleteValidation` (`pkg/registry/core/namespace/storage/storage.go:252-253`). No state changes, but the conditionally authorized caller receives the object body. Fix: document it, or have the handler drop the body when the decision is conditional.

**[Nit] [code] Evaluation fan-out.** The enforcer calls `EvaluateConditions` (an ACR webhook round-trip when not builtin) for every `deletecollection` item, every `GuaranteedUpdate` conflict retry and the too-large retry (`staging/src/k8s.io/apiserver/pkg/endpoints/handlers/update.go:229-237`), with no per-request memoization (`conditionsenforcer.go:112`). It is the same class as validating webhooks, but one request can produce N ACRs. Fix: document; consider bounding it.

### Bugs

**[Important] [code] Audit annotations are first-writer-wins, so a denied request can be audited as `decision=allow`.** `conditionsenforcer.go:116-121,137-139`; `staging/src/k8s.io/apiserver/pkg/audit/context.go:351-353`.
- With deletecollection, or an update retried on conflict, the first evaluation that allows records `decision=allow, reason=<r1>`. A later evaluation that denies cannot overwrite it (klog warning only), and the client gets 403.
- The author flagged this in the TODO (`:117-118`) but merged it.
- Why it matters: audit is the authoritative record of authorization outcomes.
- Fix: record per-evaluation outcomes under a distinct key, or write the final decision once at the end of admission (e.g. a deferred annotation keyed on the returned error).

**[Nit] [code] With the gate on, a nil authorizer makes every admission request fail with 500.** `withAuthorization` returns the handler without attaching a decision when `a == nil` (`authorization.go:66-69`), and the enforcer (default-on in generic servers, `server/options/admission.go:97-98`) then errors "a decision must be part of the context" (`conditionsenforcer.go:85-88`). This affects any generic server with `Authorization` unset and the gate on. Removal of the branch is deferred to kubernetes/kubernetes#143440. Fix: attach `Allow` in the nil-authorizer branch too, or resolve #143440.

**[Nit] [code] A 403 for a conditional decision with possible outcomes {Deny, NoOpinion} carries an empty reason.** `Reason()` is "" for conditional decisions (`staging/src/k8s.io/apiserver/pkg/authorization/authorizer/conditions.go:256-262`), so the filter emits `Forbidden(..., "")` and audit `reason=""` (`authorization.go:186,217-221`). Fix: synthesise a reason, e.g. "conditional decision cannot evaluate to Allow".

**[Nit] [code] Metrics never record the final outcome of a conditional decision.** `authorization_attempts_total{result="conditional"}` is counted at the filter (`metrics.go:139-140`) and the enforcer records nothing, so there is no way to measure conditional allow/deny rates. {Deny, NoOpinion} is reported as `denied` (`metrics.go:147-148`). Fix: add an enforcer-side counter.

**[Nit] [code] Gate-on behaviour change in the legacy filter.** A second `WithAuthorization` in one request now returns 500 (`authorization.go:101-108` via `context.go:93-95`); in 1.37 it worked. The doc already says "shouldn't run twice" (`:60`). Fix: none needed; release-note it.

**[Question] [code] Connect requests evaluate conditions against `*Options` objects.** POST `pods/exec|attach|portforward` and POST/PUT/PATCH/DELETE `*/proxy` are classified true (verb create/update/…, resource `pods`/`nodes`/`services` not excluded). Neither the conversion nor the condition model ("object is the options") is documented or tested. Fix: test it and document the `object` binding for CONNECT.

**[Nit] [code] Unreachable branches with no tests.** The SAR "unsupported client-handled decision types" 400 (`subjectaccessreview/rest.go:114`, SSAR `:125`, LSAR `:123`) is unreachable because handwritten validation rejects every set not ⊇ {Allow, Deny, NoOpinion} first (`staging/src/k8s.io/apiserver/pkg/apis/authorization/validation/validation.go:79-82`; `rest_test.go:453-500` asserts the 422). The conversion fold in `helpers.go:278-285` is likewise untestable. Fix: keep them as defense in depth and say so in comments.

**[Nit] [code] With the gate on and the enforcer disabled, SelfSAR describes a decision the server will not honour.** SAR keeps returning `conditionalDecision` (`selfsubjectaccessreview/rest.go:111-113`; integration matrix runs with the enforcer disabled, `conditionalauthorization_test.go:1012-1014`), while real requests are folded by the legacy filter (`server/config.go:1077,1086`). ## 5. Verdict

The filter → ctx → enforcer machinery is locally sound for alpha:
- Every inspected path inside a normally routed, locally served admission request fails closed (missing decision, impossible evaluation, evaluation error, conditional {Deny, NoOpinion}).
- Gate-off behaviour matches 1.37 apart from the visible default-on plugin and Go signature changes.

The weakness is the classifier's global contract, "true ⇒ enforced later". It is not true on HEAD:
- Aggregated-API writes are proxied with only a conditional allow and no enforcement in kube-apiserver.
- Unsafe corrupt-object deletes skip admission entirely.
- Side-effecting and message-returning admission plugins run before authorization is final.

Before beta:
- Make the classifier exclude non-local groups, and make the delete handler refuse unsafe deletes under a conditional decision.
- Fix first-writer-wins audit.
- Pin the authorizer snapshot in ctx and unify the gate source for the filter and the enforcer.
- Implement or explicitly drop conditional update→create.
- Rewrite the KEP's enforcer-placement, aggregated-API and SAR-disclosure sections.
- Add negative end-to-end tests (no RBAC grant) that a classified-true request with an allow-only conditional never succeeds without the enforcer.

The single most important finding is the first Security item: aggregated-API writes are classified conditions-capable while kube-apiserver never evaluates their conditions.
