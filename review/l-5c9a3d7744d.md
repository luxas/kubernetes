## What this commit does

Relocates authorization API v1/v1beta1 support code (validations, defaults, register.go, scheme registration) from `pkg/apis/authorization/…` to `staging/src/k8s.io/apiserver/pkg/apis/authorization/…` so the webhook authorizer inside `k8s.io/apiserver` can call the same validation/conversion helpers without an import cycle through kubernetes/kubernetes. Also introduces a v1 conversion step in the three SAR REST handlers (`localsubjectaccessreview`, `selfsubjectaccessreview`, `subjectaccessreview`) — they now convert the internal `authorizationapi.SubjectAccessReview` to `authorizationv1.SubjectAccessReview` before calling the shared validation function.

## Findings

### Critical (must fix before merge)

None.

### Important (should fix)

1. **The internal→v1 conversion added to each REST handler introduces a serialization step in the hot path of every `SubjectAccessReview`.** `pkg/registry/authorization/subjectaccessreview/rest.go:68–72` (and identical additions in `localsubjectaccessreview/rest.go`, `selfsubjectaccessreview/rest.go`). Every SAR — including cache misses, VAP secondary checks, and aggregated-API-server forwards — now runs a scheme conversion pass. Whether this is measurable in practice depends on the internal API version; conversion for identical internal-to-v1 structures is cheap. However, at high QPS this is an added allocation and copy. Consider whether the shared validation helper could instead accept the internal type via an interface, or use a build-time typed pointer conversion (both internal and v1 have the same shape). At minimum, verify with a benchmark that this doesn't regress SAR latency.
2. **The conversion error `"unexpected, could not convert internal SubjectAccessReview to v1"` is treated as a 500 (via `fmt.Errorf`).** `rest.go:70–72`. A conversion failure here means a scheme wiring bug, so 500 is appropriate. But the error surfaces the internal type name to the client — verify this is not information leakage. Since only cluster-admins have SAR create permissions, this is likely OK.
3. **The move breaks any external tool that used to import `k8s.io/kubernetes/pkg/apis/authorization/validation`.** The new import path is `k8s.io/apiserver/pkg/apis/authorization/validation`. Include a note in release notes; consider a deprecation shim in `pkg/apis/authorization/validation/` that re-exports for one release cycle if we care about external users.
4. **`pkg/apis/authorization/v1/register.go` (and v1beta1) are thinned but the `AddToScheme` there may still be exported for legacy compatibility.** If someone imports both the old and new packages, they may register the same GroupVersion twice. Sanity-check via `go test` and by comparing `types_swagger_doc_generated.go` behaviour before/after.
5. **The move also affects the `hack/tools/instrumentation/documentation/documentation-list.yaml`** if that ever hard-codes package paths — verify no follow-on codegen surprises.

## What's well done

- The move sets up a clean import direction: `k8s.io/apiserver` becomes self-contained for authorization API handling, without needing to reach into `k8s.io/kubernetes`. This is a prerequisite for the webhook-authorizer changes in `f1e726ca22c`.
- Explicit conversion to `v1` before validation is defensive — if a v1beta1 request comes in, it'll be up-converted first and validated once, ensuring consistent behaviour across API versions.
- The added top-of-function comment about "written only once, for the most recent external API version" is exactly the kind of anchor comment that helps future authors avoid duplicating validation across API versions.
