## 3. Adversarial review

### Security

- **[Important] [code] Cost budget is per condition with no per-request total.** Location:
  `staging/src/k8s.io/apiserver/pkg/admission/plugin/cel/authorization_conditions.go:52,168`.
  - `activation.Evaluate` gets the full `RuntimeCELCostBudget` (10,000,000, `apis/cel/config.go:26`) on every call, and
    the returned remaining budget is discarded.
  - One `ConditionsMap` may hold 128 conditions (`conditionsmap.go:116`), so one webhook leaf can spend
    1.28·10⁹ cost units per write request, more across a Union.
  - VAP threads `remainingBudget` across all expressions of one policy evaluation (`cel/condition.go:83-85`,
    `policy/validating/validator.go:128,141`), so this environment is about 128× more permissive than the VAP
    environment it claims to mirror.
  - The expression is remote input from a trusted authorizer, but many authorizers translate user- or tenant-authored
    policy into conditions. Only the request deadline bounds this (`InterruptCheckFrequency`, `compile.go:213`).
  - Why it matters: it exhausts API server CPU on the write path, per request, with a cache-hot SAR response.
  - Fix: keep `remainingBudget` in `celAuthorizationConditionsEvaluator` and decrement it across `EvaluateCondition`
    calls. Exhaustion should be an error result. This resolves the TODO at `:52`.
- **[Important] [code] The CEL expression is parsed, checked and planned on every `EvaluateCondition`, with no cache.**
  Location: `authorization_conditions.go:163`.
  - That is up to 128 × 10 KiB (`MaxConditionBytes`, `conditionsmap.go:119`) compiled per webhook per request.
  - Webhook SAR responses are TTL-cached (`webhook.go:161`), so the same expression strings recur and are recompiled
    each time.
  - Compilation is not covered by the runtime cost budget at all.
  - Also contradicts KEP 2319 ("same magnitude as `ValidatingAdmissionPolicy`"), which precompiles at policy load.
  - Fix: a bounded LRU of `CompilationResult` keyed by `(expression, OptionalVariableDeclarations)` on the builder. The
    env is fixed per builder; a compiled program is immutable, so the cache is safe to share.
- **[Important] [code] "Builtin error ⇒ unevaluatable ⇒ webhook" preserves the outcome only if the webhook can reproduce
  the in-process environment, which it cannot.** Location: `webhook.go:963-972`.
  - The rewrite catches every error class: compile errors, runtime errors such as missing keys, cost-budget exhaustion,
    and `CELValue` failures. The KEP justification (`kep.md:1573-1581`) covers only "no such function", and says the
    authorizer "will lead to the correct result".
  - The ACR request (`webhook.go:494-516`) carries no `namespaceObject` and no handle to the API server's authorizer.
    Conditions that use `namespaceObject` or `authorizer` therefore cannot be re-evaluated equivalently by the webhook.
  - The integration suite shows this. The compound-authz and `namespaceObject` rows run only the `in-process-eval-only`
    variant (`conditionalauthorization_test.go:841,859,879,903`), because the webhook-side evaluator could not pass
    them.
  - Consequences: in a skewed HA control plane, or when the evaluator could not be built (C5), the same request can get
    a different decision depending on which API server handles it. An expression that errored in-process at runtime
    gets whatever the webhook's possibly naive CEL does, instead of the in-process rule (Deny-effect error ⇒ Deny,
    `evaluate.go:144-146`).
  - With the ACR endpoint down, the result still fails closed: the deny condition stays in the refined decision, so
    `FailureDecision()` is Deny. So this is outcome divergence, not fail-open by itself.
  - Fix: defer only compile-time errors (undeclared reference or overload), which are the skew signature, and keep
    runtime errors as `Error`. Otherwise document in the KEP (see K4) that conditions using `namespaceObject` or
    `authorizer` must be reproducible by the authorizer.
- **[Question] [code] Q4 settled: the PossibleDecisions check against the refined decision, and the FailureDecision drop
  from Deny to NoOpinion, are correct and safe.** Location: `webhook.go:424-428,545-560`.
  - `partiallyEvaluateConditionsMapInternal` only removes conditions or folds (`evaluate.go:134-191`); the Union branch
    only refines sub-decisions or truncates after an unconditional leaf (`evaluate.go:240-277`). So
    `PossibleDecisions(refined) ⊆ PossibleDecisions(original)`. The webhook-side guard is therefore at least as strict
    as before.
  - The enforcer still guards against the original decision (`conditionsenforcer.go:145-150`), and so does the union
    against the original sub-decision (`union.go:163-166`).
  - The drop to NoOpinion matters only on ACR failure. It turns a pre-PR Deny into a fall-through to later authorizers
    (`union.go:173-181`). That is a legitimate outcome only if "in-process false" is authoritative, which ties it to S3
    and S5.
  - No test covers it (Te1).
  - Suggest: state the ⊆ property in the doc comment at `:424-428`, and say that an ACR outage then falls through.
- **[Question] [code] `namespaceObject` comes from the informer cache, and an in-process `false` on a Deny condition is
  final (no webhook).** Location: `authorization_conditions.go:91,133`.
  - A namespace label change propagates with informer latency. That is the same TOCTOU as VAP, but here it is an
    authorization decision.
  - A missing namespace makes `EvaluatorForData` fail, which skips builtins for the whole decision (`webhook.go:958-961`).
  - Question: is cache staleness acceptable for Deny conditions? Document either way.
- Checked and found sound (no finding):
  - The `authorizer` variable is the root authorizer that the filter stored in context (`authorization.go:170` →
    `webhook.go:956`).
  - It runs as the request user (`activation.go:81-82`), the same as VAP.
  - It is narrowed to `UnconditionalAuthorizer` (`caching_authorizer.go:38-48`), so a secondary check can never return
    or recurse into conditions. The webhook's own legacy `Authorize` does not advertise conditional types.
  - The cache key covers verb, ns, group, version, resource, subresource, name, path, field and label selectors, and
    user name, uid, sorted groups and sorted extra (`caching_authorizer.go:90-137`). Its lifetime is one
    `EvaluatorForData` call, so there is no cross-request or cross-user sharing.
  - `authorizer.serviceAccount(…)` lets a condition probe arbitrary service-account permissions, as VAP already allows.
  - Nothing is exposed that VAP cannot see: there is `object`, `oldObject`, `request`, `namespaceObject`, `authorizer` and
    `authorizer.requestResource`, but no `params` and no `variables` (`compile.go:251-265`).
  - Using `StoredExpressions` without NewExpressions validation lets a webhook use any function in the binary, as
    intended by the skew design.
  - With no decision in ctx (only out-of-tree callers; SAR registries never call `EvaluateConditions`),
    `ConditionallyAuthorizedDecisionFrom` returns a nil interface (`context.go:103-106`). `authorizer` is then
    undeclared, compilation fails, and the condition is deferred.
  - A builder-construction error returns a nil interface (`authorization_conditions.go:55,58`), not a typed nil.
  - The refined decision sent over ACR contains no new data.

## 4. Properties observed

- P1: For every input decision `d`, `PossibleDecisions(tryEvaluateUsingBuiltins(d)) ⊆ PossibleDecisions(d)`
  (`evaluate.go:134-191,240-277`; `webhook.go:951-973`). Not tested directly.
- P2: No builtin `Error` result reaches `PartiallyEvaluateConditionsAwareDecision` from the webhook: every `IsError()`
  becomes Unevaluatable (`webhook.go:968-970`). So a builtin error never produces Deny on its own. Tested by
  `webhook_conditional_test.go:TestEvaluateConditions_Builtins/in-process evaluation error`.
- P3: If the refined decision is unconditional, no ACR request is sent (`webhook.go:443-445`). Tested by
  `TestEvaluateConditions_Builtins/fully evaluated` and integration `inProcessOnlyAuthorizer`.
- P4: When ACR is sent, the request decision is the refined decision, never the original
  (`webhook.go:449,461`). Tested by `TestEvaluateConditions_Builtins/partially evaluated`.
- P5: The ACR response decision must belong to `PossibleDecisions(refined)`, else `FailureDecision(refined)` plus an error
  (`webhook.go:545-560`). Not tested for refined ≠ original (Te1).
- P6: The decision returned by the enforcer belongs to `PossibleDecisions(original)`, else Deny "failed closed"
  (`conditionsenforcer.go:145-150`). Tested by the enforcer tests (#141959).
- P7: `FailureDecision(refined) == Deny` iff the refined decision still contains a Deny condition or leaf
  (`conditions.go:224-229`, `conditionsmap.go:103-111`). In particular a Deny condition whose builtin evaluation errored
  keeps the failure decision at Deny. Not tested with builtins.
- P8: `EvaluatorForData` returns an error iff the data is nil, the data is not `*admission.VersionedAttributes`, the
  namespace lookup fails, or activation fails (`authorization_conditions.go:80-109`). Tested by
  `TestAuthorizationConditionsEvaluatorBuilder_EvaluatorForData`, except the activation-failure case.
- P9: The CEL `authorizer` and `authorizer.requestResource` variables are declared iff `apiServerAuthorizer != nil`
  (`authorization_conditions.go:102-104,114`; `compile.go:261-265`). Tested by
  `TestAuthorizationConditionsEvaluator_EvaluateCondition/authorizer variable is undeclared without an authorizer`.
- P10: Every CEL secondary check uses `versionedAttr.GetUserInfo()` (or an explicit `serviceAccount()`) through an
  `UnconditionalAuthorizer`, so it never yields a conditional decision (`activation.go:81-82`,
  `caching_authorizer.go:38-48`). Tested by integration "cel authorizer compound authorization - allow/deny".
- P11: The lifetime of the secondary-check cache is one `EvaluatorForData` call, that is one
  `(webhook, EvaluateConditions)` pair (`authorization_conditions.go:103`, `webhook.go:957`). Tested within a
  single call by `TestAuthorizationConditionsEvaluator_CachesAuthorizerChecks`.
- P12: The `apiServerAuthorizer` given to the builder is the same object the filter stored in context, or a nil
  interface when there is none (`authorization.go:170`, `context.go:103-106`, `webhook.go:956`). Tested by
  `TestEvaluateConditions_Builtins` and `TestEvaluateConditions_BuiltinsWithoutContextAuthorizer`.
- P13: `EvaluateCondition` returns Unevaluatable for a nil condition, a type other than `authorizer.kubernetes.io/cel`,

- P14: A successful evaluation's `EvalResult` is a CEL bool, because compilation rejects any output type other than
  `bool` (`compile.go:188-205`; `authorization_conditions.go:186-188`). So `== celtypes.True` (`:177`) is total. Not

- P15: Each condition's runtime cost is at most `RuntimeCELCostBudget`. There is no bound on the sum per request other

- P16: The builder is non-nil iff the gate is on, `webhook.conditionsReview` is set, and the informer factory and client

- P17: The webhook `EvaluateConditions` is reached only through the gated enforcer or the union. No SAR registry calls it
  (census, `C-symbols-and-callsites.md` §1.1).

## 5. Verdict

The fail-closed structure holds for alpha:
- The refined decision can only shrink the possible outcomes.
- Every guard (webhook against the refined decision; union and enforcer against the original) still applies.
- An ACR outage still yields Deny whenever a Deny condition is left unresolved.
- The secondary-check `authorizer` is the root chain, runs as the request user, is unconditional, and is cached per call.

The PR is not ready to merge as is, for two reasons:
- The in-process evaluator is about 128× more permissive than VAP on runtime cost, and recompiles webhook-supplied
  expressions on every request. Both are cheap to fix (shared remaining budget; compile LRU), and the first is the
  PR's own TODO.
- Three self-review threads are open (11, 13, 20), and three are only partially addressed (8, 12, 14).

Before beta:
- Narrow "any builtin error ⇒ defer to webhook" to compile-time skew errors, or fix the KEP to say what an ACR-side
  evaluator receives for `namespaceObject` and `authorizer`. Today a deferred condition cannot be re-evaluated
  equivalently.
- Decouple in-process CEL from `conditionsReview` (KEP 1247-1255).
- Add metrics and logging for deferrals.
- Implement `RecognizesCondition`.

The single most important finding is S1/TODO `:52`: a per-condition, not per-request, CEL cost budget for remote-supplied
expressions in the write path.
