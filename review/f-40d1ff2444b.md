## What this commit does

Replaces the `unconditionalDecision Decision` field on `ConditionsAwareDecision` with a private `decisionType conditionsAwareDecisionType` field, where `conditionsAwareDecisionType` is a new package-private enum with five variants: `Deny(0)`, `Allow(11)`, `NoOpinion(12)`, `ConditionsMap(13)`, `Union(14)`. Deliberately picks distinct integer values from the classic `Decision` enum (0/1/2 → 0/11/12) to avoid any accidental cross-cast confusion. Zero value still `== Deny` to preserve `ConditionsAwareDecision{} == ConditionsAwareDecisionDeny()`.

- Tests: none touched (all still pass because the API surface is unchanged — only the private field changed).

## Findings

### Critical (must fix before merge)

None.

### Important (should fix)

1. **Two `ConditionsMap` and `Union` variants are declared but no constructor produces them yet.** `conditions.go:38–42`. This commit reserves the enum values but the follow-up commits (`9d7f6593151`, `d725c326bcd`) introduce the actual variants. Between now and then, calling e.g. `ConditionsAwareDecision.IsConditionsMap()` (if such a predicate existed here — it doesn't yet) would always return false. No user-facing bug because the constructors don't exist, but audit tools that check "no dead code" may flag the unused constants. Minor.
2. **`IsUnconditional()` is now essentially a triple-OR over three enum equalities.** `conditions.go:130–132`. Consider `return d.decisionType == conditionsAwareDecisionTypeAllow || d.decisionType == conditionsAwareDecisionTypeDeny || d.decisionType == conditionsAwareDecisionTypeNoOpinion` — reads slightly better than three method calls, or use a small switch. Purely stylistic.
3. **The `String()` method's fallthrough behaviour becomes riskier now.** In commit 01 the `String()` method's `default` branch printed as `Deny`. Now that the enum can carry `ConditionsMap` and `Union` variants, that fallthrough will print those as `Deny` — actively wrong. Not a bug in *this* commit (no `ConditionsMap` value can be constructed yet), but the string formatter must be updated in the commit that introduces `ConditionsMap`. Flag for cross-check on `9d7f6593151`.

### Nits

- Enum values `11`, `12`, `13`, `14` are chosen for anti-conflation with the `Decision` int enum (`0`, `1`, `2`). Consider spelling out the reason at the top of the const block (currently only individual constants have the "different value" comment) — future readers refactoring may want to renumber to `iota`-based.
- Godoc on `conditionsAwareDecisionType` says "small enum-like type for keeping track" — Go conventionally calls this simply an "enum" via `type X int`. The extra qualifier is fine but could be shortened.
- `Reason()` / `Error()` docstrings updated to note "empty string / nil for conditional decisions" — good foresight.

### Questions

- Could the field simply have been renamed `decisionType` while keeping type `Decision` (the classic enum), reserving high integer values? The current design uses a *different* type (`conditionsAwareDecisionType`) so no accidental cross-assignment is possible. This is stronger typing and the right call — just confirming the intent.

## What's well done

- Splitting the enum into a package-private type is exactly the right move: `Decision` is the public 3-value API, `conditionsAwareDecisionType` is the internal 5-value carrier. No API surface change; representation change contained.
- The zero-value alignment `conditionsAwareDecisionTypeDeny == 0` preserves the "zero value is Deny" invariant established in commit 01 without any acrobatics.
- The comment `It is zero such that ConditionsAwareDecision{}.IsDeny() == true` on `conditionsAwareDecisionTypeDeny` (`conditions.go:32–33`) documents the load-bearing invariant precisely.
