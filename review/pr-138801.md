## 3. Adversarial review

### Security

**[Important] [code] Every narrowed site's safety rests on an undocumented contract for `Authorize`.** Location: `staging/src/k8s.io/apiserver/pkg/authorization/authorizer/interfaces.go:84-88`.
- *What happens:* The 29 `UnconditionalAuthorizer` enforcement sites (appendix C §2.2) are safe only because `Authorize` on a conditions-capable authorizer never returns `DecisionAllow` for a request it would only conditionally allow. Today only the webhook implements that rule, inline at `webhook.go:259-272`: an unrequested `conditionalDecision` becomes `FailureDecision()` plus an error, and an explicit `Denied` wins. Neither `UnconditionalAuthorizer` nor `UnconditionalAuthorizer.Authorize` documents the rule; `Authorize` has no doc comment at all. The `Authorizer` doc (`:90-102`) only says callers *choose* which handle to pass. `UnconditionalPartsOrFailClosed` (`conditions.go:181`) is the helper meant for this, and it has zero production callers.
- *Why it matters:* An out-of-tree conditions-aware authorizer (or a future in-tree one) can implement `Authorize` as "Allow if any policy, conditional or not, could allow". That compiles, passes the `var _` assertion, and fails open at every narrowed secondary check: RBAC escalate/bind, GC, NodeRestriction, CSR signer, create-on-update, impersonation and CEL `authorizer.check()`.
- *Fix:* Document on `UnconditionalAuthorizer.Authorize` that it MUST return an unconditional answer and MUST fold a would-be-conditional result to `FailureDecision()` (never Allow). Point implementers at `UnconditionalPartsOrFailClosed`.

**[Important] [code] Between the two merges, out-of-tree `SetAuthorizer` plugins silently received no authorizer.** Location: `staging/src/k8s.io/apiserver/pkg/admission/initializer/initializer.go:95-99`; the gap is between `9d011e034bf` (2026-05-08) and `0d50fdfe28b` (2026-07-28).
- *What happens:* Discovery is a dynamic type assertion, so a plugin with `SetAuthorizer(authorizer.Authorizer)` still compiled and simply was not initialized. The breakage was loud only if the plugin had `var _ initializer.WantsAuthorizer = …` (compile error) or a nil check in `ValidateInitialization`, which all 7 in-tree plugins have (e.g. `gc_admission.go:305`) so the server refuses to start. A plugin that instead guards with `if p.authz != nil { check }`, or lazily skips, **skipped its secondary authorization check (fail-open)**. One without a guard would panic at admission time.
- *Which releases:* Commit dates put v1.37.0-alpha.1 (2026-06-11), alpha.2, alpha.3 and beta.0 (2026-07-20) inside the window. rc.0 (2026-08-06) is after it. I could not verify whether the release-1.37 branch at rc.0/1.37.0 contains #140916: there are no local tags or release branch, and CHANGELOG-1.37 has no #140916 entry.
- *Fix:* For future interface renames, keep the old interface next to the new one in the same PR. Consider an "action required" release note for anyone who consumed 1.37 pre-releases.

**[Question] [code] Create-on-update's secondary `create` check is unconditional while the primary `update` decision may be conditional.** Location: `staging/src/k8s.io/apiserver/pkg/endpoints/handlers/update.go:258-279` (handle narrowed by this PR via `RequestScope.Authorizer`, `handlers/rest.go:86`).
- *Case 1, conditional `create` grant:* The webhook `Authorize` returns `FailureDecision()` + error, so `withAuthorization` answers 500 (`update.go:275-276`) rather than evaluating the condition or answering 403.
- *Case 2, conditional `update` grant:* The `update` decision in ctx is evaluated by the enforcer against admission attributes whose operation is `Create` with no old object (`update.go:213`). So the conditions written for `update` are enforced on a create.
- Both cases fail closed, but neither is specified anywhere, and the integration rows for update-to-create are commented out (shipped.md fact 9).
- *Fix:* Decide and document the semantics. Most likely: make the create check conditions-aware, or at least map the unrequested-conditional error to 403.

The other security checks found nothing:
- No production code type-asserts an `UnconditionalAuthorizer` back to `Authorizer`. `git grep '\.\((authorizer\.)?Authorizer\)'` over `pkg plugin cmd staging/{apiserver,apiextensions-apiserver,kube-aggregator}`, non-test, returns nothing. So the narrowing cannot be bypassed in-tree.
- The webhook response cache key is `json.Marshal(r.Spec)` (`webhook.go:359`). It includes `AuthorizationOptions`, so a conditional response cached for `ConditionsAwareAuthorize` can never be served to an `Authorize` caller. A conditional response is cached as authorized only when `handlesConditional` (`webhook.go:414`).
- No conditional decision can reach a UA site through the reload, metrics or union wrappers: `union.go:83` and `reload.go:88` call children's `Authorize` only.

### KEP alignment

**[Important] [KEP] The KEP's "Core interface changes" section describes a different interface design.** Location: `review/kep.md:558-680` vs `interfaces.go:84-124`.
- *The KEP says:* "change `authorizer.Decision` to be a struct … change the `authorizer.Authorizer` interface accordingly, and let the caller signal its conditions-readiness" (`kep.md:560-562`), with `Authorize(ctx, a) (Decision, error)` plus an embedded `ConditionSetEvaluator` (`:571-579`) and `Attributes.ConditionsMode()` (`:592-611`).
- *The code has:* the legacy `(Decision, string, error)` `Authorize`, a separate `ConditionsAwareAuthorize` returning a new `ConditionsAwareDecision`, and `EvaluateConditions` inline. Conditions-readiness is signalled by *which method is called* and, statically, by *which interface the caller holds* (`UnconditionalAuthorizer` vs `Authorizer`). `ConditionsMode` does not exist in code (`git grep ConditionsMode` is empty). The KEP never mentions `UnconditionalAuthorizer`, `WantsUnconditionalAuthorizer` or the narrowing strategy.
- *Verdict: fix KEP.* The two-interface design avoids rewriting every `return DecisionAllow, "", nil` (the KEP itself notes this is tedious, `:665-668`), keeps the zero-value semantics, and gives a compile-time audit of which callers can see conditions. Reviewers accepted it (T1/T2/T5).

**[Important] [KEP] The KEP's fold-down for conditions-unaware callers is a plain answer; the code returns an error, which becomes a 500.**
- *The KEP says:* "an authorizer is advised to return `Deny` if it would have returned one or more `effect=Deny` conditions, otherwise the authorizer should `NoOpinion`" (`kep.md:672-675`), and "it is up to the authorizer if it should fold … to either `NoOpinion` or `Deny`" (`:1913-1915`).
- *The code:* `webhook.go:264-267` folds with `FailureDecision()` *and* an error. Every narrowed caller that follows the decision-then-error rule therefore answers 500 (`filters/authorization.go:115-118`, `update.go:275`, `authorize.go:55`).
- *Verdict: fix KEP.* A webhook that returns conditions it was not asked for is breaking the protocol, which the KEP itself rules out at `:1610`. Flagging that as a server error is defensible. The KEP should state it, plus the 500 status, as the contract for `UnconditionalAuthorizer` callers.

**[Nit] [KEP] The KEP's call-site list (`kep.md:1854-1907`) disagrees with the shipped handles for kubelet and pod connect.** The list says the kubelet `InstallAuthFilter` "would support conditions" and pod `ensureAuthorizedForVerb` "would be conditions-aware". This PR narrowed both to `UnconditionalAuthorizer` (`pkg/kubelet/server/auth.go:45`, `pkg/registry/core/pod/rest/authorize.go:38`), and nothing later widened them. Fix KEP: mark both as "unconditional in alpha, revisit for beta", and annotate each list entry with the handle type it holds.

## 5. Verdict

The in-tree code this PR merged is sound for alpha. It is a pure type narrowing with no runtime change. On HEAD no narrowed site can receive a conditional decision, because no code casts back to `Authorizer` (P3), the built-in authorizers lift `Authorize` (P4–P5), the webhook folds unrequested conditions with fail-closed semantics (P6), and the cache is separated (P7). Every site that was narrowed is correctly unconditional for alpha. The KEP-listed exceptions (kubelet, pod connect) and create-on-update are unconditional-only by choice, and that choice should be recorded. The sites that should have been narrowed but were not (`token.go:75`, `storage_core.go:78`, `EvaluatorForData`) came in later and do not weaken anything. The real costs fall outside the tree. First, the `WantsAuthorizer` rename-then-restore left a roughly 11-week window, spanning 1.37 alpha.1–beta.0, in which out-of-tree `SetAuthorizer` plugins silently got no authorizer; that is fail-open for plugins that guard checks with `!= nil`. Second, the concrete `SetAuthorizer` methods are still gone on HEAD and the release note does not mention them. Before beta: rewrite the KEP "Core interface changes" section to describe the two-interface design and the fold-with-error contract, decide the create-on-update semantics, and add the release note. The single most important finding: the safety of all 29 unconditional enforcement points depends on P8, "`Authorize` never returns Allow for a conditionally-allowed request", and no interface or doc states it (`interfaces.go:84-88`). It must be written into the `UnconditionalAuthorizer` contract before third-party conditions-aware authorizers exist.
