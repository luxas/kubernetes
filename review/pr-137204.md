## 3. Adversarial review

### Security

**[Important] [code] Webhook `ConditionsAwareAuthorize` is not equivalent to `FromParts(Authorize)` when the webhook cannot handle conditions, and the "MUST" rule is enforced nowhere** -- `webhook.go:286-292,326-345` vs `webhook.go:255-272`; rule at `authorizer/interfaces.go:109-113`.
With no `conditionsReview` configured (`handlesConditional == false`), the webhook is conditions-unaware in effect. Its two methods still diverge:
(1) `ConditionsAwareAuthorize` turns `status.evaluationError` into the decision's error (:331-345), while `Authorize` ignores it (:259-272).
(2) `ConditionsAwareAuthorize` runs `CombinedValidateSubjectAccessReviewCreate` and fails closed on a malformed status (:326-328); `Authorize` does not validate.
With the gate on, the classifier sends write requests to `ConditionsAwareAuthorize` (`filters/authorization.go:163-164`). A pre-existing webhook that answers `denied:true, evaluationError:"…"` now gets **500 instead of 403** (`authorization.go:211-214`). A NoOpinion+evaluationError folds through `ToDecision` with its error aggregated (`conditionsunion.go:166`) and also gives 500. `responsewriters.InternalError` (`.../responsewriters/errors.go:84`) then **sends the webhook's `evaluationError` text to the requesting client**. Before this change that text never left the server. Reads keep the legacy path, so the same user and webhook get 403 on GET and 500 plus the webhook's internal text on PUT.
Why it matters: the interface promises that "conditions-aware callers … get the same output as if they called Authorize". Nothing in code or tests checks that promise, and the one authorizer whose behaviour depends on configuration breaks it. The leaked text can reveal webhook policy internals.
Suggested fix: when `!handlesConditional`, have `ConditionsAwareAuthorize` return `FromParts(w.Authorize(ctx, attr))`, or drop `evaluationErr` and the extra validation. Add an equivalence test (see Tests).

**[Important] [code] A reload between authorization and admission evaluates conditions with a different authorizer than the one that wrote them** -- `pkg/kubeapiserver/authorizer/reload.go:92-99`.
`ConditionsAwareAuthorize` and `EvaluateConditions` each call `r.current.Load()`. The request context stores the reloadable resolver, not the snapshot (`filters/authorization.go:170`, `enforcer:112`). If the authorization config reloads while a request sits between the filter and the enforcer (mutating webhooks can hold it for seconds), the new union looks up sub-decisions by name only (`union.go:188-193`). A webhook named `foo` whose URL, ACR endpoint or policy changed, or a `foo` that is now a different authorizer type, then evaluates conditions it did not write. If the name is gone, evaluation fails closed (`union.go:190-191`).
Why it matters: KEP:1975-1976 says "An authorizer only ever evaluates its own conditions." The `PossibleDecisions` guards (`union.go:163`, `enforcer:148`) limit the outcome to the decisions the original map allowed, but within that set the result comes from a different policy. An Allow-capable map can be allowed by the new endpoint.
Suggested fix: store the resolved `current.Load().authorizer` snapshot in the request context (for example through a `Snapshot()` method on the reloadable resolver that the filter calls), so evaluation uses the same chain.

**[Nit] [code] Internal error strings, including `ErrorConditionEvaluationNotSupported`, reach clients** -- `enforcer:128`, `filters/authorization.go:213`.
`apierrors.NewInternalError(err)` puts `err.Error()` in the 500 body. That body can contain "condition evaluation not supported", union authorizer names (`union.go:180`) and webhook text (see above). This is the existing pattern for 500s, but the conditional path adds new sources.
Suggested fix: send a generic message to the client and log the detail.

Checked with no further finding: the gate-off path (no production caller of the new methods; the SAR registries clear options when the gate is off, shipped.md §1); FromParts on out-of-range `Decision` fails closed to Deny plus an error (`conditions.go:110-116`); the zero value is Deny (`conditions.go:36,132`); the only production `AuthorizerFunc` that reaches request context is paired with an unconditional Allow (`filters/authorization.go:71,104`), so its `EvaluateConditions` cannot be reached from the enforcer (`enforcer:97`).

### Bugs

**[Important] [code] `apiserver_authorization_decisions_total` no longer counts "terminal decisions": a conditional request is counted twice, and non-terminal Allows are counted** -- `metrics/metrics.go:39,97-133`; `union.go:114,193`; wrapper installed per authorizer at `reload.go:132-248`.
Each configured authorizer is wrapped in `instrumentedAuthorizer` and placed in the union, so `nameToAuthorizer` holds the instrumented wrappers. Consider one write request where webhook `w` returns a ConditionsMap and RBAC then allows:
(1) `w` gets `decision="conditional"` +1 at the filter;
(2) RBAC gets `decision="allowed"` +1, even though the final result depends on `w`;
(3) at the enforcer, `w` gets `allowed` or `denied` +1 again.
If `w` evaluates to Deny, the counters show an RBAC "allowed" and a webhook "denied" for one denied request. In 1.37 RBAC would not have been consulted. The help text (:39) still says "terminal decisions".
Why it matters: dashboards and alerts that sum `allowed` per authorizer, or compare `denied` against request counts, give wrong numbers once the gate is on. Nothing tests this (see Tests).
Suggested fix: record a distinct label (for example `conditional_allowed` / `conditional_denied`) in `EvaluateConditions`, or record only at evaluation time and fix the help text. Document that a sub-decision made before an unresolved conditional is non-terminal.

**[Nit] [code] The metric records the raw decision from `EvaluateConditions` before the caller's guard rewrites it, and the two paths disagree on out-of-range decisions** -- `metrics/metrics.go:119-131` vs `union.go:163-165`; `metrics.go:90-91` vs `metrics.go:105-107` + `conditions.go:110-116`.
(1) An authorizer that returns Deny for a map without Deny gets `denied` recorded, and union then turns the result into NoOpinion "failed closed". This happens with the Deny+NotSupported default after a reload, or with a misbehaving webhook.
(2) An out-of-range `Decision` is recorded `unknown` through `Authorize`, but `denied` through `ConditionsAwareAuthorize`, because FromParts has already folded it to Deny.
Suggested fix: record `error`/`unknown` when `err != nil` together with Deny, or move recording after the guard.

**[Nit] [code] (focus c) Deny + `ErrorConditionEvaluationNotSupported` is safe for every current caller, but it does not match the `FailureDecision()` convention that the conditions-aware implementations follow** -- `authorizer/interfaces.go:118-119,143-145`; the 9 unaware implementations (C §1.1); contrast `webhook.go:431,438,456` and `union.go:135,191`, which return `decision.FailureDecision()`.
The callers on HEAD:
- `enforcer:146-150`: an impossible Deny becomes Deny "failed closed" plus an error, which is 500 either way.
- `union.go:161-165`: when Deny is impossible, Deny is rewritten to `FailureDecision()` = NoOpinion with an error, and the chain continues. That gives the same result as returning `FailureDecision()` directly.
- `reload.go:97-99` and `metrics.go:118-133` pass the result through.
- No SAR path calls `EvaluateConditions`.
So no caller fails open, and for an unguarded out-of-tree caller Deny is the strictest choice. The cost: the contract tells unaware authorizers to return a value that can lie outside the input's `PossibleDecisions`. Every caller must therefore guard, but the interface doc does not say so (:116-123). The metric records the pre-guard Deny (previous finding).
Suggested fix: either say in `Authorizer.EvaluateConditions` doc that callers MUST clamp the result to `decision.PossibleDecisions()`, or change the unaware default to `decision.FailureDecision(), "", ErrorConditionEvaluationNotSupported`.

Checked with no further finding: `reload.go:92-99` handles `current` atomically per call (one `Load()` per method; the cross-call problem is above); the instrumented wrapper returns the delegate's values unchanged (`metrics.go:98,114,119,132`); `FromParts` aggregates a nil `err` correctly (`utilerrors.NewAggregate` drops nils, `conditions.go:111-116`; tested at `conditions_test.go:165-173`).

### KEP alignment

**[Important] [KEP] The "Core interface changes" section no longer describes the code** -- KEP:560-657 vs `authorizer/interfaces.go:84-145`, `conditions.go:49-118`.
Differences:
- The KEP makes `Decision` a struct, and `Authorize` returns `(Decision, error)`. The code keeps `Decision int` (`interfaces.go:231`) and adds a separate `ConditionsAwareDecision`.
- The KEP adds `Attributes.ConditionsMode()` (KEP:589-610). The code has no mode: the caller picks a method (`interfaces.go:112-113`), and the webhook advertises `handledDecisionTypes` on the wire (`webhook.go:286-292`).
- The KEP's `ConditionSetEvaluator.EvaluateConditions(ctx, *ConditionSet, ConditionData) (Decision, error)` (KEP:581-588) became `EvaluateConditions(ctx, ConditionsAwareDecision, ConditionsData) (Decision, string, error)`.
- `Decision.Evaluate`, `AllConditionSets`, `ChainedDecisions` and `CanBecomeAllowed` (KEP:619-657) do not exist. Their closest replacements are `PossibleDecisions().Has(Allow)` and `ConditionsAwareDecisionUnion`.
- The `UnconditionalAuthorizer` split (from T13) is absent from the KEP.
Each change was deliberate: T9, T10, T11, T13, O1. **Fix KEP**: the code shape went through API review with liggitt, enj and deads2k (overview, liggitt 2026-05-26).

**[Important] [KEP] KEP: a conditions-unaware client gets a folded Deny or NoOpinion (403). Code: the webhook returns `FailureDecision()` plus an error, which is a 500** -- KEP:676-680 and KEP:1913-1918 vs `webhook.go:263-267`; `UnconditionalPartsOrFailClosed` (`conditions.go:181-198`), which implements the KEP behaviour, has no production callers.
This is shipped.md Q1. The webhook sends `authorizationOptions` only when it can evaluate. A conditional answer to a request that did not advertise support is therefore a protocol violation, and an error is defensible. **Fix KEP**: say that an unrequested conditional answer is an authorizer error and gives 500. Then remove `UnconditionalPartsOrFailClosed`, which follows liggitt's T21 rule, or give it a caller.

**[Question] [KEP] The two normative rules this PR introduces are missing from the KEP, and the KEP leaves the unaware-evaluation decision open** -- `authorizer/interfaces.go:109-113` (MUST use FromParts; callers call only one of `Authorize`/`ConditionsAwareAuthorize`), `:118-119` (Deny + NotSupported); KEP:575-578 says only "just return an error saying 'unsupported'".
**Fix KEP**: add both rules to "Authorizer requirements" (KEP:1908). State that the unaware decision is Deny and that callers clamp it to `PossibleDecisions` (see Bugs). Also state that an authorizer able to handle conditions but not configured for it (the webhook without `conditionsReview`) counts as unaware. The Security finding above shows why that last point matters.

**[Nit] [KEP] The KEP lists evaluation latency and error-rate metrics; the code has only a decision counter** -- KEP:2245-2248, KEP:2328-2330 vs `metrics/metrics.go:34-43` (only `decisions_total` gains `conditional`). The enforcer and `EvaluateConditions` paths have no latency histogram. The filter's existing `authorization_duration_seconds` covers only the authorize phase (`endpoints/filters/metrics.go:92`).
**Fix code before beta**: add an evaluation-duration histogram and an evaluation-error counter per authorizer, or reduce the KEP to what exists.

### Clarity / completeness

**[Nit] [code] The `ConditionsAwareAuthorize` doc over-promises reason and error** -- `authorizer/interfaces.go:106-107` says "the error and reason is part of the Decision struct". For ConditionsMap and Union, `Reason()` is "" and `Error()` is nil (`conditions.go:255-268`), so a conditional union that cannot reach Allow loses the sub-authorizers' reasons and gives a 403 with an empty reason (`filters/authorization.go:186-187,215+`). **[Nit] [code] MUST vs should** -- `interfaces.go:109` says MUST for `ConditionsAwareAuthorize` but `:118` says "should" for `EvaluateConditions`. Both rules are equally load-bearing for composite authorizers. Suggested fix: use MUST in both, or state the caller-side clamp.

Since `AuthorizerFunc` is how callers lift an `UnconditionalAuthorizer` into an `Authorizer` (`filters/authorization.go:71`, `path.go:50`), the doc should say that it is always conditions-unaware.

## 5. Verdict

The merged code is sound for alpha in one respect: no path fails open. Every new method on an unaware authorizer is a one-line FromParts or Deny+NotSupported, gate-off behaviour is unchanged, and every production `EvaluateConditions` caller clamps to `PossibleDecisions`, so a Deny default can only make outcomes stricter. The PR still sets up three problems that later PRs inherited and must fix before beta:

- The central contract, "`ConditionsAwareAuthorize` of an unaware authorizer MUST equal `FromParts(Authorize)`", is documentation only. No conformance test checks it, and the webhook without `conditionsReview` already breaks it. With the gate on, writes get 500 instead of 403, and the webhook's `evaluationError` text reaches clients.
- The reloadable resolver separates the authorizer that authored conditions from the one that evaluates them, contrary to KEP:1976.
- The new metric code is untested, and its semantics changed: conditional requests are counted twice, and non-terminal Allows are counted.

The KEP's "Core interface changes" section must be rewritten to match the shipped shape, which reviewers approved deliberately. **The most important finding is the unenforced FromParts equivalence and the webhook divergence (`webhook.go:286-345` vs `:255-272`).**
